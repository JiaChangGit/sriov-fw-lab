閱讀路線與實作練習

本教材以一筆 FILL 請求為主線：先建立可執行環境，再追蹤資料如何進入裝置、完成結果如何公開， 最後分析 reset 如何使舊工作失效。閱讀結果應能由命令、程式碼位置、狀態值和測試結果共同核對。

在 GitHub 直接開啟各章 Markdown，即可閱讀表格、程式片段與 Mermaid 圖。 handbook.html 是下載後使用瀏覽器開啟的離線合訂本；GitHub 的檔案頁面顯示 HTML 原始碼。 圖的語法與 GitHub 支援方式見 GitHub 圖表文件。

1. 前置知識與補讀位置

閱讀程式前，至少應能解釋 C 的指標、陣列、struct、bit mask、函式指標、回傳碼與資源生命週期。 操作環境需要基本 shell 命令、工作目錄、程序、檔案描述符，以及 Make target 的概念。 還不熟悉 PCI、VFIO、IOMMU 時，可先從下表建立最小概念，再進入實作。

概念 在此專案的精確意思 對應閱讀
PF / VF PCIe function；PF 提供管理入口，VF 提供可分配的資料入口。分出 VF 不等於已建立 DMA 隔離 系統分析
Driver guest Linux 內的核心模組 toy_pf.ko；管理 PF、協調交易與 lease Kernel 導讀
fwcore portable C 裝置控制邏輯，管理 VF FSM、ledger 和 mailbox；QEMU 以 adapter 呼叫它 原始碼導讀
VFIO guest 核心提供的裝置存取介面；tenant 以 fd、ioctl 管理 VF、DMA mapping 與 IRQ 工具與技術
IOVA 裝置發出 DMA 時使用的位址；由 requester 對應的 IOMMU domain 轉譯，不能當成 CPU pointer 位址與權限
SQ / CQ SQ 存提交描述元，CQ 存完成紀錄；兩者有各自的 producer / consumer 進度 追蹤練習
Fence 阻止特定 VF 繼續 DMA 的裝置條件；須與 cancel、generation 和 readback 一起分析 系統指南
Epoch / session / token 識別不同生命週期的工作；用途和更新時機不同，不能合併成一個模糊的「版本號」 重置追蹤
Artifact 一次執行留下的命令、輸出與結果。公開包不附本機 raw logs，重跑後才會產生相應路徑 驗證紀錄

這裡的「firmware」主要指 fwcore 所實作的控制邏輯，不表示正在刷寫實體裝置。 UEFI app 則在 guest Linux 啟動前執行，驗證開機階段的 probe 與 handoff；兩者的執行環境不同。

3. 每一段程式都回答同一組問題

讀碼時先選定一個具體輸入，例如 VF 0 的 FILL，或 RECOVERING 狀態下的舊 callback。 每走過一個函式，就填入下面的表；沒有證據的欄位保留為「待確認」。

欄位 要寫的內容
入口 誰觸發？一般 call、timer、MMIO、IRQ 或 ioctl？在哪個程序與 context 執行？
輸入 VF、request id、IOVA、length、epoch；位元組順序與值域是否已檢查？
Guard 拒絕的條件與回傳碼；檢查失敗之前是否已改變狀態？
狀態 哪些欄位讀取或更新？更新者是 core、driver、device 還是 owner？
副作用 是否配置資源、DMA、發布 CQ、送 IRQ、扣 quota 或釋放 mapping？
返回與失敗 呼叫者如何處理回傳碼？已取得的資源由誰回收？
證據 原始碼位置、測試輸入、result 欄位或同一次執行的 log

例如「DMA 已失敗」仍不足以判斷整筆操作。必須再區分 SQ fetch、payload read/write、 CQ body 與 CQ phase 哪一次失敗；它們的狀態、可見性和回報途徑不同。 具體分支見 程式追蹤與除錯方法。

4. 先預測，再核對

先遮住答案，寫下推論及程式依據；核對後修正錯誤的那個環節。 第一次可以沿完整範例逐項填表；第二次只看入口與輸入，自己補齊中間狀態； 隔一段時間，再換一個失敗條件重做。這種要求自行回想並提供核對機會的練習， 參考 CMU 的 retrieval practice 說明。

問：VF 狀態是 ACTIVE，是否足以讓它 DMA？

答：不足。還要檢查有效 configuration、BME、fence、kill 和工作世代等條件。 先在 device/toy_hw.c 找 gate()，再查 dma()、toy_irq() 與 toy_complete() 的檢查位置。 狀態表描述合法生命週期，資料 gate 決定此刻能不能做副作用。

問：舊 descriptor 的 epoch 不符，SQ_HEAD 前進後 CQ_TAIL 一定也前進嗎？

答：不一定。此專案消耗 stale descriptor 並增加計數，卻不對舊工作 DMA payload 或 CQ。 所以 SQ 與 CQ 的 index 可以不同，計算 slot 時須各用自己的 counter。 到 ring 練習手算一次，再找裝置分支與 owner 消費邏輯核對。

問：看見 eventfd 可讀，能否立即認定某個 request 成功？

答：不能。eventfd 是通知，owner 仍須檢查 CQ phase、request id、epoch、status， 以及該操作預期的資料內容。通知次數與完成紀錄數量不是同一個計數。

問：UNMAP 成功、fd 都關閉，是否足以證明 VF 已可重用？

答：還要核對裝置狀態、outstanding work、PCI presence、quota、lease 與隔離條件。 CPU 端資源回收不能單獨證明裝置端已安全收斂；B001 的時間累積案例正好說明這個差異。

問：單元測試通過，能否略過 VM 驗收？

答：不能。fake HAL 可精確檢查 core 的輸入輸出與不變條件，卻未執行 guest PCI、 VFIO TYPE1、IOMMU 和中斷的真實整合路徑。每一層測試能支持的結論見 系統分析。

5. 讀完一個 BUG 的核對題

選 BUG_LOG中的一個案例，先自行回答：

  1. 最早的異常是 compiler error、程序錯誤、裝置狀態、DMA fault，還是 validator 判斷？
  2. 哪項觀測能區分兩個可能原因？缺少哪一項證據就不能下結論？
  3. 修正改變的是產品行為、測試前置條件、觀測時點，還是判讀規則？
  4. 哪個條件必須維持，才能避免「讓測試變綠」卻削弱隔離？
  5. 需要重跑哪個最小案例，以及哪一組受影響整合測試？

答案應能連到程式與證據，而非只重述「已修正」。歷史 log 路徑用於辨識當時執行； 公開 checkout 沒有這些本機檔案時，不把缺檔當成新的故障，也不宣稱已自行重現。

從來源建置與除錯

適用環境：實體 RAM 16 GB、Windows 11、WSL2 Ubuntu 26.04。 專案內容是 M0–M3：portable core、QEMU SR-IOV 裝置、guest PF driver、VFIO tenant、 UEFI handoff 與 T01–T10 隔離／生命週期驗證。以下從相依套件與來源開始建置， 每一階段都列出命令、輸出位置和成功判斷。實際驗收版本及建置方式見 VALIDATION.md。

第一次閱讀的順序是：本章完成環境與建置 → 系統分析 看責任和圖 → Kernel 導讀 認識 driver → 逐函式追蹤 跑過一筆請求 → DEMO 手冊 實際操作 → 系統指南 查閱設計與限制。 遇到問題，先找本章最後的症狀表，再看 真實 BUG 紀錄。

本章假設讀者能在終端機切換目錄、讀取檔案，並能辨認 C 的函式與結構；不預設已使用過 Kbuild、QEMU、VFIO 或 EDK2。工具的參數、產物與執行模型另見 建置工具與執行環境。完成本章後，應能從一個失敗的 stage 找到 對應來源、實際命令和第一個錯誤，並判斷它屬於環境、編譯、映像封裝、開機或測試契約。

開始前：要建立什麼

你不需要購買支援 SR-IOV 的網卡，也不需要把筆電 GPU passthrough 給 VM。 WSL 裡的 QEMU 用 TCG 模擬 x86 CPU 與 toy PCIe device；QEMU 內的 Linux 執行真正的 PF driver、VFIO ioctl 和 IOMMU 路徑。資料工作只有 FILL（寫固定 byte）與 CRC32（讀資料計算 checksum）。 簡單工作負載讓隔離、錯誤處理與 reset 更容易逐 byte 驗證。

名稱 本章使用的定義
PF / VF PF 是管理 function；VF 是分配給 tenant 的資料 function；此模型最多八個 VF
Driver / module Linux 核心程式；本專案的 toy_pf.ko 只載入 QEMU 裡的 Linux
VFIO guest kernel 提供的介面，讓 userspace 擁有 VF、配置 DMA mappings 與中斷
IOMMU / IOVA 依裝置 requester 身分轉譯 DMA 位址；IOVA 不是 C pointer
SQ / CQ Submission Queue 存請求；Completion Queue 存完成結果
Gate 程式要求通過的驗收關卡；另有硬體 DMA gate，兩者要依上下文區分
Artifact 一次建置或測試留下的 command、log、result、hash；不是只截一張 PASS 圖

首次下載和編譯需要網路與足夠磁碟；guest 測試不需要外部網路。整套流程包含 Linux、QEMU、 EDK2 建置與多輪 VM，應安排數小時的工作窗口；實際時間依 CPU、磁碟、快取與熱節流而變。 不要把其他機器的耗時當成 timeout 標準。全程保持筆電供電，關閉佔用大量 RAM 的其他 VM。

自問：QEMU 編譯成功，為何還不能說 VFIO 已正常？ 編譯只檢查 host 程式能否產生； group viability、IOMMU domain、DMA 權限及中斷，需要 L2 Linux 開機並實際執行 VFIO ioctl。

自問：為什麼不能把壞掉的 module 換成另一份 .ko 就繼續？ Initramfs 與 runner 會核對 配套 kernel、module 和映像 hashes。替換檔案改變了驗證輸入，必須重新封裝並跑相關 gate。

1. Windows 與 WSL 檢查

PowerShell：

wsl --version
wsl --status
wsl --list --verbose
Get-CimInstance Win32_ComputerSystem | Select-Object Model, TotalPhysicalMemory
Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
Get-PSDrive C, D
Get-Content "$env:USERPROFILE\.wslconfig" -ErrorAction SilentlyContinue
wsl -d Ubuntu-26.04

確認 Ubuntu-26.04 的 VERSION 是 2。wsl --status 的預設發行版不一定就是這個專案使用的發行版， 因此明確使用 -d Ubuntu-26.04。缺 .wslconfig 表示使用 WSL 預設，不是本身就有錯。

執行環境檢查後的本機紀錄位於 artifacts/environment/windows.json； CPU、記憶體與 WSL 設定依實際檢查結果判斷，不據機型名稱猜測 KVM 能力。

16 GB 機器的操作預算是 JOBS=2、一次一項大型建置、一次一個 guest。 一般 guest 1536 MiB，KASAN guest 2048 MiB。Swap 只能緩解壓力，不代替可用 RAM。 建置預算建議 8 GiB WSL RAM、6 processors、4 GiB swap；已存在的設定若可完成驗收，無須僅為配合範例而修改。 若自行調整 .wslconfig，先備份並合併其他設定，再於所有工作停止後重啟 WSL。 執行中的 build/VM 期間不要 wsl --shutdown，它會中斷測試與保存程序。 設定檔的作用範圍與重新啟動規則可對照 Microsoft WSL 設定文件。 這裡的 8 GiB／JOBS=2 是本專案工作預算，不是 Microsoft 對所有工作負載的保證。

2. 進入專案並檢查 Linux 環境

先取得公開儲存庫的 Git URL，在 WSL 建立工作目錄。下列第一行請填入實際網址； 已經有專案時，直接進入現有目錄即可。

LAB_REPO_URL='填入儲存庫的 Git URL'

如果取得的是 ZIP，先解壓縮到 WSL 的 Linux 檔案系統，再於專案根目錄執行：

git init -b main

並設定自己的 Git 顯示名稱與公開用信箱，再建立首次 commit。建置工具需要 Git 工作目錄， 不會替你設定身分；公開提交可使用 GitHub 帳號提供的 noreply 信箱。 以下以 $HOME/src/sriov-fw-lab 為例，$HOME 會展開為目前 WSL 使用者的家目錄。

原始碼應包含 Makefile、sources.lock.json、fwcore/、device/、guest/、tools/、 tests/、patches/ 與 uefi/。Linux upstream 由 fetch-sources 取得，不是頂層 kernel/。 下載的 upstream、編譯產物和歷史 artifacts 不是替代原始碼的方式。

cd "$HOME/src/sriov-fw-lab"
pwd -P
findmnt -T .
free -h
df -h .
git status --short
git rev-parse HEAD
test -f Makefile && test -f sources.lock.json

成功判斷：最後 JSON 的 status 是 PASS，artifacts/environment/wsl.json 沒有 blockers， filesystem semantics 的大小寫、symlink、executable 都成立。至少預留 60 GiB，建議 80–100 GiB。 還要檢查 Windows 的實體 backing disk 可用空間；WSL 的稀疏 VHD 顯示大容量不代表 Windows 磁碟未滿。

/dev/kvm 存在仍不代表巢狀 KVM 可初始化。本專案必要路徑是 TCG，所有主驗收明確用 ACCEL=tcg。 KVM 不在本版交付範圍，CLI 只接受 TCG；不能改成 KVM 來跳過失敗。

若工具缺失，環境檢查會列出缺項。首次安裝套件，在一般使用者的 WSL 終端機進入專案根目錄後執行：

sudo python3 tools/install_deps.py

它安裝系統 apt dependencies，保存 apt-cache、apt-get 和 dpkg-query log 到 artifacts/dependencies/。這不是每次 build 都要做的步驟，也不使用 sudo pip。 完成後回到一般 user 的 WSL shell 重跑 make env-check。

程式追蹤與除錯章另外使用 ripgrep（命令為 rg）與 GDB；這兩項不在基本 installer 清單中。 要完成這些練習，在 L1 安裝並確認工具可用：

sudo apt-get install --no-install-recommends ripgrep gdb
rg --version
gdb --version

rg 用來快速找定義與呼叫點，GDB 用來觀察已編入除錯資訊的 native 練習程式。 一般專案建置不要求使用它們；不應因 GDB 練習成功就替 VM 案例標記 PASS。

若依賴安裝因網路失敗，先看 artifacts/dependencies/ 最新一輪的 00.log～03.log 和 result.json。修正網路／套件來源後重跑同一支 bootstrap；不要把缺少套件造成的後續編譯錯誤 當成 C 程式問題。make env-check 回 BLOCKED 時，先處理 JSON 的 blockers，再往下走。

make fetch-sources
python3 -m json.tool sources.lock.json

唯一來源下載入口是 fetch-sources。downloads/ 保存 pinned upstream checkout， build/ 裡建立可套 patch 的建置工作樹；不要直接修改 immutable upstream 來修專案。

4. M0：先驗 portable core

make build-core
make verify-m0

成功判斷：artifacts/m0-latest.json status PASS，指向的 result 也 PASS； core 證據涵蓋 FSM、非法轉移 context 不變、獨立 Python oracle、ASan/UBSan、coverage 與 fuzz。 目前完整 core 基線有四個 seeds 各十萬操作、每個 fuzz target 十萬次加額外 300 秒探索。 這一步可能數分鐘，不因一段時間沒有終端輸出就判定卡死；詳細輸出寫入各步驟 log。

若 native unit 失敗，先修 core 再進 VM，因為同一 core 會連進 QEMU。 不要只看 coverage 百分比：有執行過某一行，不等於獨立 oracle 認可其結果。

5. M1：QEMU、guest kernel 與真實 VFIO

make build-qemu JOBS=2
make build-kernel PROFILE=stress JOBS=2
make build-initramfs PROFILE=stress JOBS=2
make verify-m1 PROFILE=stress ACCEL=tcg JOBS=2

每條命令成功才執行下一條。verify-m1 本身包含 build prerequisites，已完成的工作會使用 建置系統的增量處理；stamp 不符時不能只因 binary 存在就當成可用。

輸出 用途
build/qemu/qemu-system-x86_64 含 toy device 的 host QEMU
build/kernel-stress/arch/x86/boot/bzImage L2 Linux kernel，不是 WSL kernel
build/initramfs-stress/initramfs.cpio.gz BusyBox、driver module、guest programs 和實際 ELF dependencies
artifacts/m1-latest.json 指向本次 M1 結構化報告

M1 不是只看 lspci 出現四個 VF。它檢查 PCI BAR/capabilities、實際 group viability、 每個 VF 的獨立 container、TYPE1 MAP/UNMAP、反覆 enable/disable 和資源回收。 Guest 不需要外部網路。PF module 只放入 L2 initramfs，不要在 WSL 執行 insmod toy_pf.ko。

6. M2：UEFI probe 與同次開機交接

make verify-m2 PROFILE=stress ACCEL=tcg JOBS=2

工具會編譯 EDK2/BaseTools、positive/disabled OVMF variants 與 SriovFwPkg， 先做 probe-only，再測 UEFI probe → Linux 的同次開機 handoff，最後跑 disabled PCD 對照。 每次都複製該 build 配套的新 VARS；不要拿舊 NVRAM 或另一版 CODE 拼在一起。

成功判斷：artifacts/m2-latest.json 和其 result PASS，三個 mode 都有 raw serial、QMP、 CODE/VARS provenance、ESP files 和結果。UEFI application exit 0 本身不足以宣稱 Linux handoff 成功。

Negative variant 關閉 PCD 後，Linux 仍可能在既有 bridge window 中成功配置 VF。 這是本機實測觀察，測試不硬寫「必須失敗」來迎合名稱。 更多細節與 source anchors 見 UEFI.md。

完整建置包含 M0–M3。Capsule 更新、持久化模型及實體板卡操作不屬於本專案。 部分底層程式有防禦性處理，但可主張的測試覆蓋仍以 T01–T10 的實際結果為準。

第一次建置時 build/ 不存在，直接依序執行下列命令。若要驗證已有環境的乾淨重建，先等所有 build 和 QEMU 停止、保存需要的輸出，再單獨執行 make clean-build。 它會刪除已檢查邊界內的整個 build/；原始碼、upstream downloads 與歷史 logs 保留。 不要在另一個終端機仍在測試時清理。

verify-project 會先跑完整 M0（包括兩個 300 秒 fuzz exploration），建立 QEMU、兩個 kernel 與 initramfs，再跑 M3 aggregate；其中會建立 EDK2，執行兩個 M1 profile 與三條 UEFI boot path。 最後跑全部 Python validators 和 native guest regression。每一步失敗就停止；這個入口不下載來源， 也不會自動刪除 build。第 4–7 節則是拆開定位問題時的逐步版本，不必在完整入口前再重複整輪。

執行範例

前者展示 M1 的四 VF／domain 與 100 次生命週期；後者展示 T07 的 outstanding-work reset 和健康 VF。 逐步操作、結果讀取程式及現場講解順序見 DEMO 手冊。 兩者各自產生新的 artifacts；它們不是完整測試的捷徑。若要展示同 IOVA 隔離，使用 make verify-t04； 要展示舊 callback 跨 reset 被擋，使用 make verify-t08。查看已保存結果時，應核對其版本與時間。

9. 讀懂一次測試的證據

先看 aggregate result 的 status，再追 path，不要只看某段 log 的 PASS 字串。 例如 M3 一次 run 通常有以下檔案：

檔案 回答的問題
result.json exit code、timeout、cases、build/evidence hashes、unexpected reports 是否成立？
command.json 真正執行了哪個 QEMU、kernel、initramfs、profile、accelerator？
kernel.log Linux boot、driver、IOMMU fault、KASAN/lockdep 等是否異常？
serial.log 哪個 owner、VF、epoch、lease、request、MAP/UNMAP 在何處失敗？
qemu.log 實際 VF requester、FLR、fence、core transition、DMA/callback 在何處？
m3-barriers.json / qmp.jsonl fault 是否真正 ACK？觀測是否由裝置回覆？

所有 Linux gate 都使用雙 UART：UART0 的 kernel.log 保存核心診斷，UART1 的 serial.log 保存測試 JSON 與雙向 checkpoint。UEFI handoff 的 kernel.log 還包含前面的 firmware probe， 因此從該檔追 PROBE_PASS → HANDOFF_START → Linux version；Linux 測試事件再看 serial.log。 Probe-only 不啟動 Linux，仍把 firmware 輸出放在 serial.log。這項差別由 runner 處理，不需手改 QEMU 命令。 只看 guest 最後的 PASS 不夠：B020 的 guest PASS 曾因 raw JSON 被切斷而被 host 正確拒收。

不同 run 不混用證據。程式修正後開新目錄重跑，原始 FAIL 保留。 aggregate 尚未完成時，result 可能仍是 provisional FAIL、後續 steps NOT_RUN； 程序被中斷後不能把 prefix 的 PASS 自動當成全輪 PASS。

10. 常見症狀的定位順序

症狀 先檢查 原因與處理
PowerShell 找不到 make / gcc 所在層、wsl -d Ubuntu-26.04 建置命令應在 WSL；不要另裝 Windows compiler 替代
Git 或 shell script 出現 CRLF 問題 source checkout、.gitattributes、configure log fetch 固定 LF；不要全域更改 Git 後盲目重試
Kernel EFI stub 編譯失敗 build argv 的 CC/HOSTCC、D007 pinned Linux 與 GCC 15 相容性已見失敗；使用 lock 中 GCC 14
EDK2 assembly 失敗 BaseTools/NASM 版本、D009 原始決策 保留工具版本與原始錯誤，套用已記錄 compatibility 處理
guest 找不到已打包的執行檔 ELF interpreter 與 recursive shared libraries 路徑存在但 loader 缺失也會像找不到檔案；檢查 initramfs manifest

沒 completion SQ_HEAD、CQ_TAIL、flags、epoch、QEMU DMA log 先區分沒 fetch、payload fault、CQ fault、IRQ 通知問題
reset 後 ESTALE 實際 FLR、session/epoch、ready_gen open/close 可能 FLR；新 queue 必須重新 latch/config/rearm

這張表包含一般診斷策略，不表示每一項都在本機重現。已重現的 BUG、原始失敗、修正及回歸 另列於 BUG_LOG.md，平台決策另列於 DECISIONS.md。

一次失敗要保存哪些內容

  1. 命令與所在層：是在 PowerShell、WSL 還是 guest；保存真正的 argv 和 exit code。
  2. 最早的錯誤：compiler 第一個 error、kernel 第一個 warning、或第一筆不符合契約的 event。 最後的 make Error 2 通常只是上游失敗的結果。
  3. 當時的輸入：Git commit/dirty state、source/patch hash、kernel profile、accelerator 與 case。
  4. raw logs：保留整個 run 目錄；不要先手工刪行再把清理過的 log 丟給 validator。
  5. 修正後的新 run：小範圍重現先通過，再跑受影響 gate；新結果連到原 FAIL，兩者都保留。

記憶體不足時，cc1: fatal error: Killed signal 或 exit 137 只是一個線索。 在 WSL 查 free -h、dmesg／可取得的核心紀錄，再對照 Windows RAM 壓力；確定是 OOM 才調整工作量。 先停掉其他大型工作並保持 JOBS=2；必要時用 JOBS=1 重建。 不要用關閉 sanitizer、忽略 warning 或加大所有 timeout 來掩蓋原因。

建置工具與執行環境

本章回答三個問題：每個工具把什麼輸入轉成什麼輸出、產物在哪一層執行，以及失敗時該檢查 哪個邊界。操作順序見 從來源建置；本章的檢視命令均在 L1 WSL 的 repository 根目錄執行，並假設對應的建置步驟已完成。

先掌握 C 的函式、結構、指標、整數型別，以及 Linux 的程序、fd 和檔案路徑即可開始閱讀。 第一次出現的系統名詞會在其用途旁解釋。讀完後，應能指出 .a、.ko、ELF、bzImage、 initramfs 和 OVMF 之間的關係，並把同一個「找不到檔案」症狀拆成可驗證的不同原因。

1. 三層執行環境：同樣是 Linux，責任不同

層 實際執行者 可觀察的資源 本專案的用途
L0 Windows Windows 與 WSL 管理程式 實體 RAM、磁碟、WSL VHD 提供外層資源，啟動 WSL
L1 WSL Linux GCC、Python、QEMU 程序 host fd、工作目錄、QEMU 記憶體與 Unix sockets 建置、模擬與收集證據
L2 QEMU guest Linux kernel、toy_pf.ko、labd、tenant guest PCI、VFIO fd、guest IOVA、SQ/CQ 管理 VF 並執行資料工作

toy_pf.ko 由 L1 的 Kbuild 產生，卻由 L2 的 kernel 載入。labd 和 tenant 同樣在 L1 編譯， 再打包到 L2 執行。QEMU 的 device/toy_hw.c 在 L1 QEMU 程序內執行，向 L2 呈現 PCIe 裝置。 因此，單看編譯所在的機器，無法判斷程式的執行層。

圖中的向下箭頭表示提供執行環境；向上回到裝置模型的路徑表示實際 I/O。tenant 的普通 C 指標是 L2 userspace virtual address；傳給裝置的 IOVA 屬於該 VF 的 IOMMU domain，兩者不能互換。 裝置模型內另有 L1 QEMU 的 host pointer，讀 code 時必須保留這三種位址的區別。

自問：在 WSL 對 /dev/vfio/vfio 做 ioctl，能直接觀察本專案的 VF 嗎？ 不能。 本專案的 toy VF 存在於 L2 模擬 PCI 拓樸，相關 VFIO ioctl 必須在 L2 執行。

2. Make 與 Python：排程入口和具體操作

頂層 Makefile 的 target 多半只呼叫一支 Python 工具；真正的來源準備、 compiler argv、hash 與錯誤處理位於 tools/。例如：

build-kernel:
	$(PYTHON) $(ROOT)tools/build_kernel.py --profile $(PROFILE) --jobs $(JOBS)

讀這段時依序展開：PROFILE=stress 決定輸出與設定；JOBS=2 限制建置平行度；Python 工具選定 Linux source、GCC 14、Kbuild targets 與 log 路徑。make -n build-kernel 只會顯示 這個 Python 命令，無法顯示 Python 執行時才組合的所有子命令。實際 argv 應讀當次 artifacts。

頂層 .NOTPARALLEL 限制一輪 Make 的 target 排程；builder 仍可用 -j 2 編譯多個檔案。 QEMU、kernel、initramfs、EDK2 與 VM 共用 resource_lock()，用非阻塞 flock 排除同時占用大型資源的另一輪工作。 Native core 沒有這把鎖；不要因為存在鎖就另外啟動一輪完整驗收。

自問：等待中的 terminal 沒印進度，是否一定 deadlock？ 不一定。先辨認當前 stage，讀其 .log、檢查程序狀態與紀錄的 timeout。不要用啟動第二輪驗收測試第一輪是否還活著。

3. 從 C 到可執行檔：compile、archive、link

C 的一般產物路徑是預處理、編譯、組譯，再由 linker 解析符號和配置輸出。gcc -c 在產生 object file 後停止；沒有 -c 的建置命令可以繼續連結。這些階段與停止選項可對照 GCC Overall Options。

這是一般工具鏈關係。專案的 build_core.build() 先逐檔以 GCC -O2 -c 產生 build/core/*.o， 再用 ar rcs 集合成 libfwcore.a。這個 .a 是 object archive，沒有 main() 或可直接執行的 程序入口；建立 archive 也不要求所有跨檔案呼叫已解析。之後的 unit/oracle 測試會把全部 core C sources、fake HAL 和測試入口一起編譯連結，並非執行 .a。

建置後，用 binutils 唯讀檢查產物：

ar t build/core/libfwcore.a
nm --defined-only build/core/fsm.o
nm --undefined-only build/core/fsm.o
readelf -h build/core/fsm.o
readelf -h build/core/native/unit

成功判斷：archive 可列出 core objects；fsm.o 是可重定位的 ELF；unit 是可執行程式。 啟用 PIE 的工具鏈可能把可執行檔標成 ELF DYN，不能只憑這個標籤判斷它一定是 library。 nm 列出的未定義符號表示該 object 尚須其他 objects 或 libraries 提供；若最終 link 仍無定義， 才會形成 undefined reference。

同一份 core 為什麼能進不同環境

fw_port.h 在一般 C 環境使用 <stdint.h> 型別，在 FW_UEFI 下改用 UEFI 的固定寬度型別。fw_hal.h 則用函式指標把時間、讀硬體、關 gate、 取消 I/O 等動作交給 adapter。核心演算法因此不直接依賴 Linux syscall、QEMU object 或 UEFI service；平台把對應 callback 填入 HAL。

Core builder 的 -ffreestanding -fno-builtin 宣告此程式不依賴一般 hosted C 環境的假設，並限制 對標準函式的 builtin 處理；它們不會自動替程式實作記憶體管理、中斷或硬體存取。Portable 的條件 仍包括型別、資料布局、生命週期及 HAL 契約。QEMU 和 EDK2 builder 會各自複製並編譯 core sources， 不會把 Linux userspace 測試 ELF 直接放進 firmware。

自問：修改 PF driver 之後只重建 .ko 夠嗎？ 不夠。還需把新 module 封裝進對應 initramfs，確認配套 hashes，再重跑受影響的 guest gate。

7. VFIO：fd、DMA mapping 與中斷的分工

本專案使用 Linux 6.12 的 classic VFIO group/container/TYPE1 介面。Group 是隔離與擁有權的 基本單位；container 可以容納 group 並設定 IOMMU。每個 VF 在本專案各自建立 container， 用來驗證獨立 domain；這是專案選擇。介面背景見 Linux 6.12 VFIO。

lab_vfio_open() 依序驗證 API 與 TYPE1 extension、開 group 並檢查 viable flag、把 group 加入 container、設定 IOMMU，最後取得 device fd 和 regions/IRQ capabilities。任何一個 fd 只代表取得某一層的操作入口，不能省略後續檢查。

文字順序就是 container → group → attach → TYPE1 → device → capabilities → DMA mapping。 本版 owner 經 device fd 的 pread／pwrite 存取 BAR，不直接 mmap BAR，並解析 region capabilities 來確認可用範圍；匿名 RAM 的 mmap 則用來配置 SQ/CQ/payload。 BAR 存取、DMA memory mapping 和 MSI-X 的 eventfd 設定各自完成不同工作：

操作 建立的關係 不會自動完成的事
查詢 region，以 pread／pwrite 存取 BAR tenant 可以存取裝置 MMIO 不會替 payload 建立 IOVA
VFIO_IOMMU_MAP_DMA domain 中 IOVA 到已註冊 pages 與權限的映射 不會提交 SQ entry 或打開硬體 gate
MSI-X IRQ eventfd 設定 interrupt vector 對應 userspace 可等待的通知 fd 不表示 CQ 一定已有屬於當前 request 的成功結果
寫 doorbell 告知裝置有新的 queue 進度 不代表 fetch、payload、CQ、IRQ 已全部成功

因此，收到 eventfd 後仍須檢查 CQ 的 phase、id、epoch、status、len 與預期結果； session 屬於 owner 與裝置的世代管理資訊，不是 CQ wire 欄位。反過來，沒有 eventfd 也不能立即認定裝置沒做事：可能已有 CQ、IRQ 被遮罩，或通知設定本身出錯。完整追蹤見 TRACE_CODE_ZH 與 TRACE_PRACTICE_ZH。

回收時，MAP/UNMAP 的 extent、buffer 的生命週期和 VFIO fd 必須一致。 lab_vfio_close() 檢查 UNMAP 回報的 size；若沒有完整解除 mapping， 不能先釋放仍可能被 pin 的 allocation。owner 的完整資料路徑另有其資源 ledger，閱讀時不要把 簡單 map probe 的回收流程直接套成所有 queue 的規則。

自問：兩個 VF 使用相同 IOVA 是否一定衝突？ 不一定。位址解釋取決於 requester 所屬 domain；獨立 domain 可讓相同 IOVA 指向不同 pages。要證明隔離，還需觀測實際 VF requester 與各自 payload／CQ，不能只比較 userspace pointer 或 container fd 數值。

8. EDK2 與 Linux boot：另一條平台路徑

M1 可由 QEMU 直接載入 kernel/initramfs；M2 則先執行 OVMF 和 SriovProbe，再測同次開機 交給 Linux 的 handoff。兩條路徑共享裝置與 Linux 產物，卻檢查不同初始化責任。

build_edk2.py 的建置層次如下：

  1. BaseTools 在 L1 執行，處理 EDK2 描述檔、編譯規則與 firmware 映像。
  2. SriovFwPkg 產生 SriovProbe.efi，在 L2 UEFI 環境執行並使用可攜 core。
  3. OVMF variants 產生 SR-IOV support PCD 開啟／關閉的 firmware，保留實際 build 產生的 PciBusDxe AutoGen.h，核對 PCD 是否生效。
  4. CODE/VARS 分別提供 firmware code 與 variable storage 的配套映像；runner 為每次開機 準備新的 VARS 複本，避免前次 NVRAM 狀態污染結果。

EDK2 的 GCC5 是工具鏈規則名稱，本專案用 wrapper 指向已釘選的 GCC 14。看到 build tag 不能直接推斷執行的 compiler 主版本。--prepare-only 也只代表來源準備，工具會保留建置與 runtime 尚未執行的狀態；它不能作為 M2 PASS。

自問：SriovProbe 回傳成功，是否就完成 handoff？ 尚未。還要在同輪 log 中找到 HANDOFF_START、Linux 開機、PF/VFIO 測試及 host validator 的完整結果。若只有 probe 輸出， Linux 接手和後續 I/O 仍未被證明。細節見 UEFI。

9. 閱讀失敗的固定順序

遇到失敗先做分類，再決定工具。這個順序避免把載入錯誤當成編譯錯誤，或把觀測通道損壞當成 裝置功能失敗。

問題 先確認 接著使用的工具或來源
來源是否正確 commit、patch hash、是否 dirty sources.lock.json、Git、fetch log
產物是否產生 第一個失敗的子命令及 exit code builder stage JSON／log
產物是否配套 kernel/module/initramfs hashes 與 profile stamps、runner 的 build check
程式是否可載入 ELF architecture、interpreter、NEEDED、symlink readelf、ELF closure、manifest
kernel 是否開機 UART0 的 Linux banner 與第一個診斷 kernel.log、command.json
測試是否開始 GUEST_BOOT、case、第一個 checkpoint serial.log、guest/init
裝置是否完成動作 requester、queue counter、fence/epoch、DMA 結果 qemu.log、QMP ACK、source trace
完整結果是否可接受 deadline、raw evidence、所有 case 與 validator 當輪 result.json 及其引用檔案

先用上表說明「最後已知正確的位置」，再寫下一個必須成立的條件。例如：kernel 已啟動， insmod 失敗 → 查 module 搭配與 kernel 拒絕原因；CQ 已前進，tenant timeout → 查當前 epoch、 CQ phase 與 IRQ 等待路徑。每次只修正有證據支持的原因，保留原始 FAIL，重跑後比較新的結果。

可用以下三題檢查是否掌握各層：

  1. build-core PASS，但 kernel build FAIL，哪份程式真的執行過？ L1 建置工具成功產生 core 產物；只有 verify-m0 才執行 core 驗證。Kernel 尚未產生不代表 core 邏輯錯誤，需從 kernel 首個 compiler/config 錯誤追查。
  2. build-initramfs PASS，但 VM 缺少 GUEST_BOOT，哪裡仍未被證明？ 封裝與 loader 檢查已成立，L2 開機、mount、UART 切換、module probe 等 runtime 路徑仍可能失敗。
  3. Guest 印 PASS，但 host result FAIL，要以哪個為準？ 先查 host 拒絕原因。Guest 的局部 成功訊息無法取代 raw evidence 完整性、unexpected kernel reports 與跨層契約檢查。

資料流：隔離在每次 DMA 都必須成立

相同 IOVA 並不表示同一塊記憶體。IOMMU translation 還取決於 requester 及其 domain。 SQ 是裝置讀，CQ 是裝置寫，payload 依 opcode 決定方向。每次 helper 的錯誤回傳都要處理； 成功 fetch descriptor 不保證稍後的 payload 或 CQ 也能存取。

CQ phase 是最後發布的 byte。Tenant 先檢查 phase/acquire，再讀 CQ 其他欄位及 payload， 最後更新 CQ_HEAD。IRQ 只通知「可能有新進度」，不代替 CQ 的有效性檢查。

控制時序：正常配置

  1. labd 透過 PF driver PROVISION，再由 Linux enable SR-IOV。
  2. PF lease 成立後啟動 owner；VFIO open 可能引發 FLR，owner 重新讀 session/epoch。
  3. owner MAP 自己的 buffers、建立 MSI-X eventfd、寫 staging registers 與 CONFIG_COMMIT。
  4. owner 發 READY，labd 核對 peer、lease、operation、session/epoch/ready_gen。
  5. PF REARM 核對 live hardware state，確認 RUNNING，再讓 owner 開始提交。

若步驟 3 失敗，不能直接把 lease 當成沒發生；仍要確認 fence、mapping、fd 和 child 的清理。 若步驟 5 拒絕，owner 保持停止，不能重送 descriptor 試運氣。

正常 I/O 的時間與可見性

圖中的 fetch 是 SQ 與 CRC payload 的讀取路徑；FILL 的 payload 操作是以相同 VF requester 寫入， 兩種 opcode 都經 IOMMU 並檢查每次 DMA 回傳值。 Doorbell 表示「SQ 有新工作」，不表示工作已完成。DMA payload 成功，也不表示 CQ phase 已發布。 IRQ 發生後，tenant 仍以 phase/acquire 讀取 completion；eventfd counter 不能拿來當 CQ entry 數。 本版限定 x86_64 QEMU/VFIO MMIO 路徑；換到 non-coherent 實體平台時，cache maintenance 與 DMA barriers 需要平台專屬實作和重新驗證，不能只複製 C11 fence。 即使 coherent DMA memory 也仍需要正確 ordering；參見 Linux 6.12 DMA mapping guide。 該文件說明 kernel DMA API；本專案 userspace VFIO 的具體存取順序仍應追 owner_workload()。

控制時序：有未完成請求的 reset

T07/T08 已驗證圖中的 retained work 與 stale callback，並通過完整 M3 回歸。 T06 另驗證 VFIO_DEVICE_RESET、queue readback、重新配置以及 healthy VF。 兩組測試觸發 reset 的路徑不同，不能互相替代。

Reset 時的兩個重點是「確認安全的順序」和「誰仍擁有記憶體」。PF 先關 gate/readback， core 完成 quiesce/reset 到 RECOVERING；owner 將舊 request 標失敗，完成 exact UNMAP 後， 才建立新 queue。T08 刻意把已 UNMAP 的舊 CPU allocation 保留下來做 guard， 新 allocation 使用相同 IOVA，用來觀察 callback 是否錯碰新舊 memory。

不能只看 callback counter。必須實際執行帶有舊 session/epoch/token 的 callback， 檢查 STALE_CPL 而非 STALE_DESC，並確認 payload/CQ 未改及 eventfd 沒有新通知。

FSM 與 queue gate 是兩張不同的圖

完整轉移表以 fwcore/fsm.c:edges 的 20 條為準；離線 HTML 會直接從當前來源抽取表格。 圖只展示主要路徑與失敗匯流，不能拿示意箭頭當作所有合法 state/event 的枚舉。

從 FREE 到 ACTIVE 的 PROVISION commit，表示 firmware 已分配資源。它仍要求 hardware fenced， 且沒有 live config。這時的 ACTIVE 不代表 tenant 可 DMA。真正的執行條件位於 device/toy_hw.c:gate()：要求 ACTIVE、valid config、BME、沒有 fence/kill，並有正確 generation。

QUIESCING 與 RESETTING 的 logical deadline 各 100 ticks，RECOVERING 等 READY 為 1000 ticks。 裝置一 tick 是一毫秒 QEMU virtual time。PF driver 的 mailbox 上限為 5 秒，以 guest jiffies 計時； labd／tenant 的 wire 上限為 120 秒，以 guest CLOCK_MONOTONIC 計時。它們不延長 core deadline， 也不是 WSL controller 的程序 timeout。因此可能出現「guest 管理程式仍在等待，裝置已 KILL」的狀態。

期限的精確邊界另以 native fake HAL 控制 logical clock，從正常 CREATE/COMMIT/REARM/FENCE 路徑進入 QUIESCING、RESETTING、RECOVERING，沒有直接改寫待測 deadline。 artifacts/recovery-deadlines/20261013T074437Z-7f_3jtp_/ 保存九個實際讀值及 ASan/UBSan 執行： quiesce/reset 在 99 不失敗，100/101 進 FAILED 且 KILL；READY 相應為 999/1000/1001。 這三種 timeout 情境都保留 8 credits。VM 的慢 READY 測試負責真實跨層握手；native 測試負責精確邊界， 不宣稱 QMP polling 可以準確停在每一個 VM tick。

FAILED 會保留 reserve；已驗證 owners closed、PCI/config/outstanding 清除後，DESTROY 可以釋放 ledger， 但 KILL 仍需 global recovery 才能清除。故 FREE、FENCED 和 KILLED 可同時出現， 並不是只看 FREE 就能接受為乾淨測試基線。

從一筆 FILL 建立跨層資料模型

假設 owner A 的 VF 是 requester 0101，它將 8-byte payload 映射到 IOVA 0x400000， 並提交 FILL，arg=0x79。下圖的數字是解說用輸入；不是新增的執行紀錄。 要追蹤的物件有四個：CPU allocation、VFIO mapping、SQ descriptor，以及裝置保留的 operation。 它們的生命週期不同；取消 operation 不會替 owner 解除 mapping，UNMAP 也不會替裝置刪除 operation。

實際位址翻譯由 requester 所在的 IOMMU domain 決定。圖中 A 的 CPU pointer 只用於 VFIO MAP； 裝置取得的是 IOVA，不能把 pointer 直接塞進 descriptor。PF 本身也不是 A 的替代 DMA 身分。 可由 dma() 中的 PCI_DEVICE(s->vf)，確認 SQ、payload、CQ 都使用同一個 VF。

Reset 的資料保護證明如何拆解

設定舊 operation 的 tuple 為 (session=1, epoch=7, token=9)；fence 後 live tuple 可變為 (1, 8, 10)。數值僅用來示意。安全條件不是「舊 callback 應該不會再來」，而是它即使來了也無權寫入。

  1. toy_fence() 先設 fenced=true，再取消 pending、清除 IRQ pending，最後增加 epoch/token。
  2. cancel_pending() 留下 retired 副本供測試；它不再由正常 pending 路徑完成。
  3. toy_complete() 先查 op->valid，再比 tuple。世代不符時增加 STALE_CPL，將 valid 清除後返回。
  4. 世代相符仍要通過 gate；payload DMA、CQ DMA、IRQ 各有實際執行點的檢查。
  5. Owner 在停止提交、完成 reset 協調後才撤銷舊映射。T08 保留舊 CPU allocations 作 guard， 另外配置新 allocations 並重用相同 IOVA。

因此測試要同時觀察「舊 callback 確實被呼叫」與「新舊 buffers／CQ／IRQ 都未被它更動」。 只讓 callback 不執行，不能檢驗拒絕過期 tuple 的程式；只看 STALE_CPL 增加，也不能檢驗所有副作用。

圖中的 mailbox 和 MMIO 是 guest／QEMU 邊界，不是 PF driver 直接呼叫 host 的 C 函式。 詳細函式路徑見 逐函式追蹤，重現與反證方式見 定位與修正。

自問自答：用反例檢查模型

若 A、B 的 IOVA 一樣，如何證明沒有共用 payload？ 先找不同 requester/domain 的建立證據， 再讓 A 執行可辨識的寫入，檢查 B 整個 buffer 和 B 自己的正常進度。只印出兩個 PID 或兩個 fd 不足以證明。

ACTIVE、RUNNING、owner READY 三者為何不能任選一個？ ACTIVE 管資源准入；RUNNING 反映 queue 執行設定； READY 是帶 tuple 的跨程序訊息。延遲訊息可能仍寫 READY，但 live epoch 已改變，所以 REARM 必須再核對硬體快照。

若 mutex 已確保 reset 和 ioctl 不同時執行，舊 callback 還會有問題嗎？ 會。Mutex 保護 CPU 管理操作， 不會撤回裝置已複製的 descriptor；operation tuple 與 gate 才處理這個時間邊界。

當 CQ 滿了，為何不先取 SQ 再等等？ service_one() 在 CQ capacity 不足時不 fetch SQ， 避免產生無處發布的完成結果。讀者應再檢查 pending.valid 的限制，不能只看 backlog 數量。

若 reset 後 reserve 仍為 8，是否表示 leak？ 未必；RECOVERING 保留配額是契約。 應問它是否在成功 DESTROY／RELEASE 後歸零，且 PCI、config、outstanding、lease 和 owner 都已清除。

2. 一次開機如何走到 probe

讀碼順序：

  1. tools/run_vm.py 組成 QEMU 命令，指定 guest kernel、initramfs、Intel vIOMMU 和 toy PF。
  2. Guest Linux 啟動後執行 initramfs 的 /init，也就是 repository 裡的 guest/init。
  3. init 掛載 proc/sys/devtmpfs，確認 PF 存在，再載入 /lib/modules/toy_pf.ko。
  4. module_pci_driver(toy_driver) 註冊 PCI driver。toy_ids 指定 vendor/device，PCI core 將符合且未被占用的裝置交給 probe。
  5. guest/pf/toy_pf.c:toy_probe() 建立管理資源；成功後註冊 misc device。
  6. init 由 /sys/class/misc/toy_pf0/dev 建立 /dev/toy_pf0，管理程式才有可開啟的入口。

Driver 註冊和個別裝置 probe 是不同事件。模組載入成功，不代表指定裝置一定綁定成功； T02 會另外檢查失敗 probe 沒有留下 control node，乾淨重試則確實建立 control node。 PCI driver 的 callback 結構與 probe 語意可對照 Linux 6.12 PCI 文件。

在 WSL terminal 切到 repository 根目錄後，用以下命令定位，不必先記行號：

grep -nE 'module_pci_driver|toy_ids|toy_driver|toy_probe' guest/pf/toy_pf.c
grep -nE 'insmod|make_node|labd|m1-spike' guest/init

閱讀後應能說出：誰呼叫 probe、成功時公開什麼入口、失敗時誰負責回收。

3. probe 的順序是一份資源帳本

toy_probe() 的主要步驟如下。讀每個取得動作時，立即往下找它對應的釋放動作。

步驟 實際程式 取得什麼／檢查什麼
1 kzalloc、mutex/completion/work/kref 初始化 PF context 與同步物件，尚未接觸裝置
2 pci_enable_device_mem 啟用 PCI memory resources
3 pci_request_regions 宣告本 driver 使用 BAR resources
4 檢查 BAR0 長度與類型，pci_iomap 取得可用 MMIO helper 存取的映射

4. open、ioctl、read、poll 各做什麼

guest/pf/toy_control.inc 是 toy_pf.c 納入的實作片段。先找檔案尾端的 toy_fops：

Userspace 操作 Driver 入口 主要用途
open("/dev/toy_pf0", ...) toy_open 建立 per-open context，加入 files list，取得 PF reference
ioctl(fd, TOY_GET_INFO, ...) toy_ioctl 驗證 UAPI header，讀取一致的裝置 snapshot
lease/fence/reset/rearm ioctl toy_control_ioctl → toy_execute_ctl 檢查 owner 與世代，再執行管理交易
read(fd, ...) toy_read_file 取出 driver event；無資料時依 blocking 模式等待或回 EAGAIN
poll(fd, ...) toy_poll 將程序掛入 wait queue，回報可讀或裝置移除
最後一次 fd reference 釋放 toy_release_file 回收 per-open context，降低 PF reference count

一次 open 建立一個 open file description。dup 後的兩個 fd 指向同一個 struct file， 不能把它們當成兩個互不相關的 owner。專案用 per-open context 綁 lease，也用它保存回覆 cache 和事件佇列。

閱讀 guest/pf/toy_control.inc:toy_ioctl() 時，注意四個防線：

  1. dying 表示已不能再操作 BAR，回 ENODEV。
  2. copy_from_user 先複製到 kernel local struct，再驗 size、ABI、reserved 和 VF 範圍。
  3. 可修改狀態的命令再驗 session、epoch、lease token 和 operation。
  4. 裝置成功回覆後，仍讀回 fence/config/state 等後置條件。

copy_to_user 失敗不會撤銷已經做完的 reset。控制交易保存原結果，讓相同 operation 的重試取回結果。 這是協定語意，不是單靠 system call 的正負回傳值就能解決。

5. 三種執行 context，三種限制

路徑 Context 本專案的處理
probe、ioctl、read Process context 可以在適當條件下睡眠；用 mutex 序列化管理操作
toy_irq IRQ handler 讀 cause、ACK、complete、排 work；不取得管理 mutex
toy_notify_work Workqueue 可以睡眠；取得管理鎖後讀取一致快照，向各 open context 發布事件

沿 guest/pf/toy_pf.c:toy_irq() 看 mailbox completion： handler 呼叫 complete(&pf->mbx_done) 喚醒等待者；等待者仍需核對 DONE 和 ACK_SEQ。 另一個 IRQ 先到、IRQ 被合併或回覆已過期，都不能靠「被喚醒」三個字判定交易成功。

鎖順序是 admin_mutex → mbx_mutex。Mailbox 等待期間，完成它的 IRQ handler 不取得這兩把鎖， 否則會出現等待者持鎖、完成者也等同一把鎖的循環。其他事件交給 workqueue，不在 IRQ context 做完整管理交易。

event_lock 則是短暫保護 per-open event ring 的 spinlock。 toy_read_file() 在鎖內把資料移到 stash，放鎖後才 copy_to_user；copy 失敗保留 stash， 避免 userspace 重試時事件已經遺失。完整鎖與引用表見 Trace code。

7. 物件還活著，不代表硬體還能用

kref 保護 toy_pf 記憶體的生命週期，dying 則阻止移除後的 MMIO。 兩者缺一不可：只有 reference count，舊 fd 可能讀取已解除的 BAR； 只有 dying flag，舊 fd 仍可能持有已被釋放的 context pointer。

toy_open() 在管理鎖內確認可接受新操作，再取得 reference。 toy_remove() 關閉入口、fence、同步 worker/IRQ、釋放 PCI resources，最後放掉 driver 持有的 reference； 既有 file context 仍需完成自己的 release。Reference 的取得與釋放原則見 Linux 6.12 kref 文件。

讀碼能解釋預期生命週期，但本版驗收只涵蓋已列出的 T01–T10，未涵蓋所有 hostile hot-remove 交錯。 應把「設計如何處理」和「實際測到哪些路徑」分開回答。

9. 練習題解答與下一條 trace 路徑

第一題先從 probe 的 clear_master label 往下讀。此時可能已經有 BAR mapping、兩個 IRQ 和 work， 所以要先讓裝置停止接受管理工作、同步相關執行路徑，再解除映射與釋放 context。 直接 kfree 會讓仍可能被 IRQ/work 使用的 pointer 失效。

第二題的等待者是發 mailbox 的 process context，喚醒者是 toy_irq()。 完成通知表示狀態可能有進度；DONE/ACK_SEQ 才把回覆綁到這一次 request。 這可對照正常 I/O：eventfd 同樣只是通知，CQ phase/id/epoch 才描述完成資料。

第三題的 reset 可能已經完成。若只因回傳 EFAULT 就建立新 operation 重送，可能再次產生副作用。 應理解既有 operation 的重試契約，再沿 toy_control_ioctl() 看完整 request 比對和 cached result。

第四題先畫 ownership：VFIO fd 持有 device、IRQ 與 mappings；PF lease 控制管理權限。 只有實際完成 fence、drain、UNMAP、fd close 和 owner 退出，管理端才能釋放 lease 或允許下一個 owner。 程式必須保留失敗時尚未確認釋放的資源，不能只讓計數看起來歸零。

完成這四題後，依序追下面三條路徑：

路徑 起點 終點 應記下的欄位
管理查詢 labd 的 ioctl PF SNAPSHOT 與 UAPI 回覆 session、epoch、state、reserve、flags
正常資料 owner_workload CQ 檢查與 CQ_HEAD 更新 SQ/CQ cursor、IOVA、requester、phase、id
Reset labd recovery 新 owner configuration 與 REARM lease、operation、epoch、ready_gen、cancel token

每次只追一筆請求，將成功路徑走完，再回頭選一個 return/goto 追失敗回收。 詳細函式順序與實際紀錄在 Trace code。

先分清楚程式究竟在哪裡執行

Windows 是 L0，負責執行 WSL；WSL Ubuntu 是 L1，負責編譯與執行 QEMU。 QEMU 裡的自建 Linux 是 L2，PF driver、labd 與 tenant 都在 L2。 device/ 的 C 程式在 L1 的 QEMU process 裡執行，模擬 L2 看見的 PCI 裝置。 fwcore/ 被連進 QEMU，管理這個模擬裝置的 firmware 狀態；並非在筆電上的真實網卡執行。

這個區分決定除錯位置。tenant 的 ioctl 回錯，要看 guest 的 kernel.log； 模擬 DMA 使用錯誤 requester，要看 QEMU 的 qemu.log；QEMU 本身編不過，要看 L1 build log。 在 WSL 載入 toy_pf.ko 不會連上 guest 裡的 PCI function，也不屬於本專案的操作流程。

閱讀路線與完成條件

本章假設已能閱讀 C 的指標、結構與條件分支，並會在 shell 執行命令。尚未建置時， 可以先完成靜態追蹤；動手追蹤 的 native GDB 練習不需要啟動 guest。 讀完後應能把一筆工作寫成「輸入 → 檢查 → 副作用 → 發布 → 回收」，並回答三件事：

  1. 誰持有這筆工作的身分、記憶體與完成位置？
  2. 哪個 guard 阻止它在 reset 後繼續 DMA？

關鍵程式碼：拒絕舊工作應放在哪裡

以下片段摘自 裝置執行路徑，省略 log 與未相關分支； 請回到完整函式查看所有 guard，而不要把片段當成可替換的實作。

static bool same_generation(ToyPF *pf, ToySlot *s, const ToyOperation *op)
{
    return !op || (op->session == pf->session &&
                   op->epoch == s->epoch && op->token == s->token);
}

session 區分整體裝置工作階段；epoch 與 token 區分 VF 的世代與取消邊界。 op == NULL 表示這次呼叫沒有已保存的工作 tuple；gate() 仍會檢查 live VF、fence、kill、 config、ACTIVE 與 BME。NULL 並非免除所有檢查。

if (!same_generation(pf, s, op)) {
    toy_saturate(&s->stale_cpl);
    /* 完整程式在此輸出 TOY_STALE_CPL。 */
    op->valid = false;
    return;
}
if (!gate(pf, vf, op)) {
    op->valid = false;
    return;
}

toy_complete() 將兩個檢查放在第一筆 payload/CQ DMA 前。若只在 SQ fetch 時檢查 epoch， 工作可能已被保存為 delayed operation，而 reset 已換掉 mapping；舊 callback 仍會進入後半段。 反過來，只看 gate 也不足：新世代 REARM 後 gate 已打開，必須用保存的 tuple 拒絕舊工作。

result = write ? pci_dma_write(PCI_DEVICE(s->vf), addr, buffer, length) :
                 pci_dma_read(PCI_DEVICE(s->vf), addr, buffer, length);

這裡選擇的是 s->vf。相同數字 IOVA 在不同 domain 中可指向不同的 page， 必須把 requester 身分一併追到 PCI helper，才能解釋 T04/T05 為何能驗證隔離。

自問自答： generation 正確，是否就能省略 DMA 回傳值？不能。generation 回答「是不是此代工作」， IOMMU 與 PCI helper 回傳值回答「這次存取是否被接受」；頁面可能沒有映射或權限不足。 同樣地，FW_DMA completion 的 length 是原請求長度，不是已寫入 byte 數；要判斷部分寫入，必須看 buffer 與 guard。

四種位址與兩種權限

tenant 的 C pointer 是 guest process 的虛擬位址，CPU 經 guest page table 存取它。 descriptor 裡填的是 IOVA：裝置 DMA 要使用的位址。這兩個數字不必相同。 VFIO 將 tenant buffer pin 住，讓 guest IOMMU 將某個 domain 的 IOVA 對應到 guest physical pages。 QEMU 最後再把 guest physical memory 解析到自己的 backing memory；toy 裝置不能直接跳過此路徑。

PF-only fence 決定「現在能否發 DMA」；IOMMU 決定「這個 requester 能碰哪些位址」。 BME 是 PCI Command register 的 bus-master enable，tenant 可操作自身 PCI config； 因此 BME 不能代替 PF-only fence。epoch 則用來辨認舊請求，不是位址隔離機制。

IOMMU group 是不能任意拆分的隔離邊界。本拓樸要求每個 VF 各有一個只有自身的 group； 兩個 container 若仍受同一 group 限制，不能宣稱獲得兩份隔離 domain。 T04/T05 因此同時檢查 group membership、獨立 owner、相同數字 IOVA，以及實際 requester DMA。 Group/container 的背景可對照 Linux VFIO 文件。 該網頁會隨 upstream 更新；本版實際採用的 ABI 與實作以 pinned Linux 6.12、 guest/tenant/vfio.c 及 downloads/linux/Documentation/driver-api/vfio.rst 為準。

控制流程入口：啟用 VF 之前先預留資源

從 guest/pf/toy_pf.c:toy_sriov_configure() 開始看。寫入 PF 的 sriov_numvfs 後， Linux 會進入這個 driver callback。driver 在管理序列化區段中先驗證要求值、既有 VF 數與 leases， 對每個 slot 執行 PROVISION，最後才呼叫 pci_enable_sriov()。

這個順序避免「Linux 已經公布可使用 VF，但 firmware 沒有資源」的半完成狀態。 PROVISION 不是單純設一個 enabled bit，還要管理 queue/vector/reserve 的 ledger。 權威 ledger 與 VF FSM 放在 fwcore；PF driver 保存 host transaction、lease 與觀察快照， 不另寫一份自行決定 ACTIVE/FAILED 的 firmware FSM。

繼續追 toy_mailbox_status() → QEMU device/toy_pf.c:write_pf() → toy_mbx_work() → fwcore/mailbox.c:fw_handle_mailbox()。 mailbox 的 session/sequence 與回覆 cache 處理重送；重送相同 request 不能再次預留資源。 讀到 callback 不代表已完成，還要看它回傳的 status、transaction commit 與 unwind 分支。

若第 N 個 VF 的 PCI 建立失敗，Linux 自己的 enumeration unwind 與 firmware 的 rollback 是兩件事，都必須驗證。T02 用 pinned guest kernel hook 在真實枚舉迴圈中注入失敗； 若 firmware rollback 也失敗，就留下 FAILED 與 retained quota，不能為了清表而直接寫 FREE。

一個 tenant 如何真正取得 VFIO 所有權

先讀 guest/admin/labd.c:isolated_owner_start()，再讀 start_owner()。 labd 取得 per-open PF lease、查詢 VF 的 group、啟動 child、保存 pidfd，並檢查 Unix socket 的 SO_PEERCRED。child 在 exec 前關閉管理 fd，不繼承 PF fd 或另一個 tenant 的 VFIO fd。

再讀 guest/tenant/vfio.c:lab_vfio_open()。重要順序如下：

  1. 將該 VF 綁定 vfio-pci，核對 sysfs driver link。
  2. 開啟 container，核對 VFIO API 與 TYPE1 IOMMU extension。
  3. 開啟 group，要求 VIABLE，將 group 加入 container，再設定 TYPE1 IOMMU。
  4. 取得指定 BDF 的 device fd，核對 PCI、RESET、region、IRQ capabilities。
  5. 核對 BAR 尺寸、兩個 MSI-X vectors、vendor/device identity、magic 與 IOVA 範圍。

此處的 argsz 很重要：capability 回覆可能比第一個固定 struct 大。 owner.c:region_caps() 會重新查詢實際大小，檢查 offset、範圍、重複與循環； 不能把 kernel 傳回的 offset 當成可信任的 C pointer 直接加上去讀。

VFIO open 本身可能觸發 PCI FLR。owner_open() 因此在取得 fd 後重新 latch session/epoch。 不能沿用 labd 在 open 前讀到的 epoch；這是 T06 要以真實 ioctl/open/close 驗證的重點。

建立 ring：有 CONFIG 還不能立即跑

guest/tenant/owner.c:map_buffers() 建立三種映射：

Buffer IOVA 裝置方向 VFIO flags
SQ 0x100000 裝置讀 descriptor READ
CQ 0x200000 裝置寫 completion WRITE
Payload 0x400000 FILL 寫／CRC 讀 READ＋WRITE

這裡的 READ/WRITE 是從裝置 DMA 的角度，不是 C 程式能否讀寫 memory。 T05 還揭露 pinned Intel IOMMU 對 WRITE-only 的平台差異，詳見 BUG_LOG B002， 不能用 requested flags 的列印結果代替實際權限測試。

owner_configure() 建立 eventfds、登記 MSI-X IRQ、設定 BME，再寫 staging queue registers 與 session/epoch，最後寫 CONFIG_COMMIT。QEMU device/toy_vf.c:config_commit() 驗證範圍、entries、當前 generation 及 fence，成功後成為 READY_PENDING。

tenant 送 READY 給 labd。labd 核對自己的 lease、peer、PF live snapshot、ready_gen， 透過 TOY_REARM_VF 要求 driver 重新核對，才讓裝置開 gate。 收到 RUN 訊息之後，owner_workload() 還會讀回 QUEUE_STATUS==RUNNING；Unix 訊息本身不等於硬體就緒。

追一筆 FILL：從 C array 到 PCI DMA

入口是 owner_workload()。它為每個 outstanding entry 分配獨立 payload 區， 以 lab_put16/32/64() 明確編碼 32-byte little-endian descriptor。 避免直接把 C struct memcpy 到 ring，可以排除 compiler padding、alignment 與位元組序的歧義。

CPU 填好 SQ 後執行 C11 release fence；owner_write32() 再執行 sequentially consistent fence， 經 VFIO region pwrite 寫入 register。本版只驗證 x86_64 QEMU 路徑；這些 fence 不等於跨平台 DMA coherency 保證。 程式透過 owner_write32() 存取 register；程式不 mmap MSI-X table 保留頁。 SQ_TAIL 與 DOORBELL 進入 device/toy_vf.c:write_vf()，喚醒有界 worker。

device/toy_hw.c:toy_worker() 計算 backlog、交給 core 的 logical scheduler， 再由 service_one() 取 descriptor。最重要的轉折點是 dma()： 它把 該 VF 的 PCI device 傳給 pci_dma_read/write()，所以 QEMU vIOMMU 看到的是該 VF RID。 若改成 PF 或直接寫 guest RAM，即使 FILL 的 byte pattern 看似正確，隔離契約也已經破壞。

service_one() 保存 descriptor copy、session、epoch、cancel token 與 CQ reservation。 格式不合法和 epoch 過期不同：舊 epoch 增加 STALE_DESC 並丟棄；非法 opcode/length 產生 BAD_DESC。 合法 FILL 進入 toy_complete()，先核對 generation 和 gate，才寫 payload。 跨 4 KiB 邊界時以 page boundary 切成 chunk；若後半段 fault，前半段可能已經寫入。 軟體不能把 CPU buffer 回填原樣後聲稱 DMA 沒發生。T05 guard-page 變體專門驗證這個差別。

Completion 的發布順序與 eventfd

toy_complete() 先編碼 CQ，再分別寫內容和保留 bytes，最後單獨 DMA 寫 phase byte。 phase 成功後才更新 CQ_TAIL 並呼叫 toy_irq()。toy_irq() 再檢查同一個 gate， 透過該 VF 的 MSI-X 發通知；guest 的 VFIO 將它接到 owner 註冊的 eventfd。

tenant 被 eventfd 喚醒後仍要用 acquire load 檢查 CQ phase；IRQ 是提醒，不是 completion 資料。 程式逐項核對 id、status、length、epoch、CRC、reserved bytes 與 payload guard， 最後才把 CQ_HEAD 交回裝置，允許它重用 ring slot。

索引使用 u32 累計 counter，按模 2^32 回繞，實際 array index 才取 counter & (N-1)。 phase 每圈交替，讓同一個位置的新資料和上一圈不同。 「只對 index 取模然後比較相等」無法可靠區分 empty、full 與 wrap。 native ring oracle 另用獨立 Python FIFO 比較跨 UINT32_MAX 的行為，不必真的提交四十多億筆請求。

FENCE、FLR 與 delayed completion 的先後關係

device/toy_hw.c:toy_fence() 先關 gate，取消 pending work、清除 pending IRQ， 檢查溢位後才增加 epoch 與 cancel token。同一個非零 fence token 重送時，維持 fence 並取消 pending， 但不再次增加世代；FLR 則不使用這個重送去重分支。 不能先 unmap，再希望裝置剛好沒發 DMA。toy_vf_flr() 共用 clear/cancel 邏輯， 清掉 queue registers，再送 firmware FLR event，使已存在的 VF 進 RECOVERING。

即使 callback 已排入 timer，執行時也要在真正 payload/CQ DMA 前核對原先的 generation。 toy_complete() 在第一個資料存取前檢查 same_generation()；不符只增加 STALE_CPL， 不寫 payload/CQ，也不通知 tenant IRQ。STALE_DESC 與 STALE_CPL 是不同證據，不能互相替代。 T08 的個別 VM 與完整 M3 回歸已通過；下節以保存的真實輸出追蹤它。

owner 的 mapping 最後由 owner_unmap() 解除。VFIO_UNMAP 回傳 size 必須等於要求值； 短 unmap 或失敗會把 memory 留到所有 VFIO fds 都關閉後再清理。 PF 的 ledger 歸零只能證明 firmware 資源釋放，不能證明 userspace fd、pinned pages 或 child 已退出。

3. 舊請求明確取消，舊記憶體保留作證

RECOVERY_CANCELLED 記錄 old_epoch=4、new_epoch=5、requests_marked_error=1。 它不是一筆成功 completion，也不把 completed 從 4096 偷加到 4097。

owner 先回 HELLO，等待實際 device virtual time 至少走過 200 ticks。 此時先不送 HELLO_REPLY 授權新配置。這是在 1000-tick READY deadline 內的慢 owner， 不是把 host sleep 的 200 ms 當作裝置時間。

guest/tenant/recovery.c:owner_retire() 要求三個 VFIO UNMAP 都完整返回， 把舊 CPU allocation 移入 retired 陣列，保留每個 byte 的 guard copy。 隨後 owner_configure() 配置另一組 CPU memory，在同一 container 重用相同 IOVA。 驗證器要求兩代 vaddr 不相同。若直接 free 舊 buffer，allocator 可能重用同一位址， 會失去同時檢查舊、新記憶體的能力。

4. 兩次真正呼叫舊 callback，分別跨過 fence 的前後

第一次在 fresh_config、尚未 REARM 時呼叫，第二次在 REARM 後、新 I/O 尚未開始前呼叫：

TOY_STALE_CPL vf=0 old_session=2 live_session=2 old_epoch=4 live_epoch=5 old_token=5 live_token=6 count=1
TOY_FAULT_ACK property=try-stale-cpl valid=1 ack=5 consumed=1
TOY_STALE_CPL vf=0 old_session=2 live_session=2 old_epoch=4 live_epoch=5 old_token=5 live_token=6 count=2
TOY_FAULT_ACK property=try-stale-cpl valid=1 ack=6 consumed=1

toy_complete() 先檢查 generation，再檢查 gate，因此這兩次都在世代不符時返回。 第二次在 gate 已解除後執行，用來確認新 queue 恢復運作時，舊 callback 仍不能寫入。device/toy_pf.c:stale_set() 將 retained operation 副本交給 device/toy_hw.c:toy_complete()，不是直接把 STALE_CPL 加一。

ACK 的 valid=1 指「呼叫前副本有效」，consumed=1 指「callback 已消耗該副本」。 這兩個時點曾被記成同一個值，導致 B010 的真實 validator FAIL。 最後 STALE_CPL=2、STALE_DESC=0、DMA_FAULT=0；每次檢查中 eventfd 非阻塞 read 回 EAGAIN (11)，舊、新 SQ/CQ/payload 的 bytewise guards 均不變。

5. 再證明裝置不是被整台停掉

A 新 ring 完成另一批 4096 筆，累計 8192，先前取消的一筆仍單獨計為 error。 B 在 pending、slow_ready、configured_fenced、fresh_io 四個 checkpoint 的 completed 分別為 4608、6656、7424、11776，session=2、epoch=4 沒改。 每批都驗 payload/CRC，並非只看到計數器增加。

最後先 fence 兩個 owner，再 UNMAP／關閉 VFIO／pidfd reap／釋放 lease／disable VFs。 全部八個 slot 回 FREE、reserve=0、outstanding=0、lease=0、flags=1。 這是該次情境的完整成功條件，不包含已移出本版的 hostile remove/crash 全矩陣。

不啟動 VM 也能先做的三個 trace 練習

這些是閱讀練習，不算新增的 runtime PASS。先寫下答案，再打開原始碼核對：

  1. 在 device/toy_hw.c:toy_complete() 找出第一個可能寫 payload 的點。 沿此前每個 return 分支，說明 old token、fence、BME、bad descriptor 分別在哪裡被拒絕。 如果只在 SQ fetch 檢查 epoch，延遲 completion 會留下哪個空窗？
  2. 在 guest/tenant/owner.c:owner_workload() 找出 release、phase acquire、CQ_HEAD 三個位置。 解釋為何 eventfd 成功讀取後還要 drain CQ，以及 phase 檢查不能搬到讀取 CQ body 之後。
  3. 在 guest/admin/recovery.inc:recovery_handshake() 列出所有可能回錯的 handshake 步驟。 對每一步標出當時誰持有 lease、舊 mapping、新 mapping、pending work。 說明為何出錯不能一律執行 memset 清 ledger。

重要實作一：把 bytes 安全轉成 descriptor

打開 fwcore/codec.c:fw_decode_sq()。讀法分三步：先將 local struct 清零，再以逐 byte LE helper 讀固定 offset，最後驗證後才賦值給呼叫者的 out。這讓失敗輸入不會留下半解碼結果。

SQ offset 長度 欄位 必要條件
0 8 addr addr <= UINT64_MAX - len，避免範圍相加溢位
8 4 len 1–4096 bytes
12 / 13 1 / 1 opcode / flags FILL=1 或 CRC32=2；flags=0
14 2 id 識別請求，completion 必須核對
16 8 epoch parser 只解碼；裝置另比對 live epoch
24 8 arg FILL pattern 等操作參數

不要把 bytes cast 成 packed struct：即使 x86 允許部分 unaligned access，也會把 layout 與 endianness 假設散落到各層。逐欄解碼較容易在 native fuzz、QEMU、UEFI 重用。

fwcore/codec.c:fw_queue_validate() 再檢查 N=16..256 且為 2 的次方、SQ/CQ 相同大小、64-byte 對齊、 session/epoch 相符、加法不溢位、兩段範圍不重疊。Descriptor 正確不等於 ring configuration 正確，兩層都要驗證。

重要實作二：有表格也要有 guard 的 FSM

沿 fwcore/fsm.c:fw_transition() 讀：

  1. 在 edges 找 (current state, event)。找不到時，在任何 HAL 呼叫之前回 FW_STATE。
  2. 取得硬體 snapshot，要求 fenced；需要新 deadline 時以 checked arithmetic 計算。
  3. 依 event 檢查條件。例如 RELEASE_OK 必須 PCI 不存在、config/outstanding 清除、owners_closed 為真。
  4. 只有能釋放時才扣 ledger；失敗的 release 進 FAILED，保留 reserve。
  5. 最後寫入 epoch、deadline、state，輸出 transition log。

READY_REARM 另由 fw_vf_event() 導向 rearm helper，所以不能只看 edges 就認為所有轉移都走同一 switch。 Native tests 不只數合法邊，還驗非法事件後整份 context 不變；HAL side effects 則另受 adapter 契約與測試約束。

手算一次 admission 與 quota

搭配 fwcore/admission.c:fw_create() 閱讀：先驗 VF 範圍與 reserve=1..64， 再要求 FREE、fenced、未 killed，且沒有 PCI function、live config 或 outstanding work。 所有檢查成功後，才一起更新 state、reserve、epoch 與三個 resource counters。

資源 每個 VF 取得 上限與 admission 檢查
Queue 1 現有 used_queues 必須小於 8
Vector 2 現有 used_vectors 必須不大於 14，新增後最多 16
Credit 要求的 reserve 先確認 reserve 合法，再要求 used_credit ≤ 64 − reserve

例如四個 VF 各 reserve=8，ledger 為 4 queues、8 vectors、32 credits。 把其中一個 reserve 從 8 改為 16，fw_set_reserve() 先檢查可安全相減，再算 remaining=32−8=24，最後確認 24≤64−16，才寫回 used_credit=40。 這個操作還要求 ACTIVE/RECOVERING、fenced、無 outstanding 且未 killed；有 quota 不代表可隨時修改。

用「上限減需求」檢查，比先做可能溢位的加法再判斷更清楚；但減法本身也必須先驗需求不超過上限。 回收則沿 fw_transition() 的 RELEASE_OK／ABORT_OK 檢查 ownership 後扣帳。 若 release 失敗而保留 reserve，下次 admission 仍會計入它，避免同一份資源被重複分配。 這些數值是由當前程式推導的手算例子；執行證據仍讀 M0 oracle 和 T02 的實跑結果。

重要實作三：重送與 exactly-once 的邊界

fwcore/mailbox.c:fw_handle_mailbox() 先驗非零 seq 與 live session。 如果 seq 等於最近已接受的 seq，必須比較完整 opcode、target、args；相同才回 cached reply， 不同則 SEQ_CONFLICT。比最後 seq 舊的請求回 STALE_SEQ。這是「單一 outstanding、最後一筆 cache」 的去重設計，不是無限歷史的分散式 exactly-once 系統。

PF 的 toy_mailbox_status() 寫欄位後 SUBMIT，再同時檢查 DONE 與 ACK_SEQ；單靠 IRQ 到達不能判斷 是這筆回覆。若裝置回 IDLE 且允許 retry，就重送相同 staging request，不重新做 fence 或增加 sequence。 讀者可以把「同 key 同內容」「同 key 不同內容」「舊 key」「新 session」列成四格，逐一找到 return 分支。

重要實作四：logical scheduler 與效能的區別

fwcore/scheduler.c:fw_schedule_round() 每輪最多分配 64 credits。先篩 ACTIVE、unfenced、非 killed、 BME、config_valid、沒有 delayed outstanding 的 VF，給 min(reserve, backlog) 基本配額； 剩餘以 reserve 作權重分配，先取整數，再依餘數補足，相同餘數用 round 做輪替。 需求較少的 VF 先封頂，再重算其他 VF 的份額；迴圈由八個 VF 的固定上限限制。

所有 serviced counter 先驗溢位，再一起 commit，避免半數已加、後半數失敗。 這些測試核對 logical work allocation 的規則，不能拿 credits 或 TCG wall time 當成實體裝置 bandwidth／P99。 這段邏輯由 M0 native scheduler 測試覆蓋；不包含實體裝置的 QoS 壓力或效能驗證。

重要實作五：為何 SQ index 不等於 CQ index

這個缺陷位於 guest/tenant/owner.c:owner_workload()。 例：SQ tail=6、CQ head=5，表示先前有一筆 stale SQ 被 consume，但沒有產生 CQ。 下一筆請求寫 SQ slot 6，也把 payload 放在 slot 6 對應的區段；completion 卻會寫 CQ slot 5。 若用 CQ index 找 payload，就會核對到別筆 buffer。

修正後兩個索引分開計算：

/* CQ entry 依完成游標定位。 */
uint32_t cq_index = lab_ring_index(o->cq_head, o->entries);
/* Payload 依原提交游標定位；CQ id 另行核對。 */
uint32_t payload_index = lab_ring_index(start + received, o->entries);

這是為閱讀整理的等價片段，實際變數名與 guard 以可點擊源碼為準。 tests/guest/test_owner_workload.c 執行真實 workload 函式，以模擬的 pread/pwrite device boundary 回覆 CQ；分別測正常游標、相差一筆、跨 UINT32_MAX，N=16/32/64/128/256 共 15 組。 這是 native regression；T03/T09 和完整 M3 另驗 guest 路徑。

重要實作六：Linux driver 的 UAPI、鎖與中斷

先打開 PF control 實作，由 toy_fops 找到 toy_ioctl() → toy_control_ioctl() → toy_execute_ctl()。這份 .inc 被 guest/pf/toy_pf.c 納入同一編譯單元，不是另一個 kernel module。

一筆 REARM 的閱讀順序：

  1. file->private_data 取得本次 open 的 toy_file，再取得共同的 toy_pf。
  2. 取得 admin_mutex 並檢查 dying；若裝置已移除，返回 ENODEV，不再讀 BAR。
  3. copy_from_user 只複製到 kernel local value。檢查 size、ABI major/minor、reserved=0、 VF 範圍與 command-specific flags，避免直接信任 userspace struct。
  4. operation 做 per-open replay 檢查：相同 operation 必須 command 和完整 request 相同； 舊 operation 拒絕。同一個 fd 的 cached result 和 firmware mailbox cache 是不同層。
  5. 核對 live session/epoch、lease owner/token、ready_gen，以及 FENCED、CONFIG_VALID、BME、 READY_PENDING 和 outstanding=0。每個條件回答不同問題，不能只檢查「enabled」。
  6. 發 mailbox REARM，再讀回 ACTIVE、config、epoch、fence/kill。回覆成功仍需驗證硬體後置條件。
  7. 保存結果再 copy_to_user。即使最後 copy 失敗，已執行的操作不能當作未發生；保留 cache 讓同一 operation 可取回原結果，避免重做副作用。

這是原始碼行為的解釋；本版整合覆蓋仍以 T01–T10 的實際 case 為準，不表示每種 EFAULT 時序都已注入。

接著讀 guest/pf/toy_pf.c:toy_irq()。IRQ handler 讀 cause、ACK，對 mailbox 呼叫 complete()，將其他事件累積後排入 workqueue；它不取得會睡眠的管理 mutex。 toy_notify_work() 在可睡眠的 context 取得 admin_mutex，擷取一致快照，再發布 event。 因此「IRQ 喚醒」與「查詢完整狀態」被分成不同 context，應區分各自允許做的事。

4. 為什麼 SQ slot 6 對應 CQ slot 5？

guest/common/lab_ring.h:lab_ring_index 對 entries=16 使用 counter & 15。 在這個例子裡，送出時 start=6、收到第一筆時 received=0：

提交資料位置： (start + received) & 15 = 6  → payload slot 6
完成記錄位置： cq_head & 15           = 5  → CQ slot 5

兩者用途不同。舊 epoch 的 descriptor 可以只推進 SQ、不產生 CQ； 因此用 CQ index 找 payload 可能拿到另一筆資料。現在的 guest/tenant/owner.c:owner_workload 使用 start + received 找原始 payload， 使用 cq_head 找 completion。B018 的原因與回歸見 BUG 紀錄。

下一步試算：若 entries=16、start=15、received=1，payload slot 是多少？ 答案是 0。這是 ring index 的回繞；u32 counter 本身也會回繞， lab_ring_used 以 unsigned 減法計算差值，但容量限制仍由呼叫處檢查。

7.3 什麼時候用 step、next、finish 與 watchpoint

命令 適合回答的問題 使用限制

8. 練習把錯誤縮小到一個分支

以下情境都先寫預測，再讀 service_one 與 toy_complete。 不要為了讓預測成立而修改 validator；預測不符時，先確認輸入與執行版本。

8.1 descriptor 的 epoch 與長度同時錯誤

條件：live epoch=5、descriptor epoch=4、len=0，其餘 ring 與 gate 合法。 預測 SQ_HEAD、CQ_TAIL、STALE_DESC、STALE_CPL 與 payload 的變化。

答案：SQ DMA 成功後 SQ_HEAD 先加一。parser 回 FW_BAD_DESC，但 service_one() 接著先比較 raw epoch；epoch 不符使 STALE_DESC 加一並返回，不會進 BAD_DESC completion 分支。 CQ_TAIL、STALE_CPL 與 payload 不變。這個例子說明「函式返回了錯誤」不代表呼叫者一定先處理那個錯誤。

8.2 payload 跨頁，第二頁沒有 mapping

條件：FILL addr=0x400ff8、len=16。第一頁可寫，第二頁沒有 mapping；SQ 與 CQ mapping 有效。 toy_complete() 的第一個 chunk 是 8 bytes，第二個也是 8 bytes。

答案：第一個 chunk 可能已寫入 0x400ff8..0x400fff；第二個 DMA 返回失敗後 status 改 FW_DMA。 裝置仍嘗試發布 CQ；若成功，CQ 的 length 保留原請求 16，之後 VF 進錯誤處理。 這不是「全部成功或全部回復」的交易。定位時比較 payload 前後與兩側 guard， 再對照 TOY_DMA_ERROR 的 addr、length、write 和 RID，而不能只看 CQ status。

8.3 reset 完後 gate 開啟，舊 callback 才到

條件：舊工作 tuple=(session 2, epoch 4, token 5)，live tuple=(2, 5, 6)， 新世代已 REARM，gate 其他條件合法。

答案：在 gate 檢查前就因 generation 不符返回；STALE_CPL 加一，舊工作失效， payload/CQ 與 tenant IRQ 不改變。僅檢查「reset 當下 gate 關閉」無法覆蓋此情境； T08 在 REARM 前後各嘗試一次舊 callback，目的正是檢查兩個時間窗。

8.4 找到第一個失敗後，怎麼決定修正是否成立

寫下最小重現的輸入與預期不變條件，再定位第一個偏離點。 例如 B018 的錯誤是用 CQ index 反推 payload；修正應讓 payload 依原始 SQ submission index 定位， 並保留 CQ id 核對，不能只把預期 payload 改成實際錯誤位置的內容。 接著重跑該索引差異、正常索引與 u32 wrap 的 native regression，再依影響範圍重跑 guest case。 原始 FAIL 與新一輪結果應分別保留；通過範圍以實際執行紀錄為準。

BUG 定位、反證與修正

本章把「結果不符預期」拆成可檢查的條件。命令均在 L1 WSL 的專案根目錄執行， 除非段落另有標示。歷史已發生問題見 BUG_LOG；本章的假說表和練習是排查方法， 不代表列出的每一種故障都已在本專案發生。測試結果的版本與範圍見 VALIDATION。

完成本章後，應能從一個 FAIL 找到最先失去的契約、提出至少兩個可區分的原因， 再用原始記錄與最小回歸檢查修正。先讀 系統分析 的三種狀態， 追函式時搭配 TRACE CODE。

1. 先確認失敗屬於哪一層

同樣是「沒收到 completion」，可能是 owner 沒提交、QEMU 沒 fetch、payload fault、CQ fault、 IRQ 未通知，或 tenant 讀取了錯誤的 phase。錯誤訊息中的最後一個 timeout 通常只描述等待結束， 不必然是最初的錯誤。

4. 沒收到 completion：沿資料發布順序定位

先用既有紀錄做索引，不先新增大量 printf：

rg -n 'owner_workload|__ATOMIC_ACQUIRE|CQ_HEAD|SQ_TAIL|DOORBELL' guest/tenant/owner.c guest/common/lab_ring.h

最後兩行用來找原始碼入口；符號搜尋沒有輸出時，先確認命名與檔案，不能推論該邏輯沒有實作。

最後確認的進度 下一個要觀察的條件 能區分的原因
lease 已取得 owner 的 MAP、CONFIG_COMMIT、READY tuple、REARM 回覆 管理已准入，但 queue 尚未開啟
SQ tail 已前進 gate、CQ capacity、pending.valid、SQ head 尚未 fetch，或先被 backpressure 擋住
SQ head 已前進 descriptor epoch、STALE_DESC、decode status 被消費不表示會產生 completion；舊 epoch 特別不寫 CQ
payload DMA 成功 CQ body／phase 寫入結果 payload 成功後仍可能在 CQ 寫入失敗
CQ phase 已發布 tenant 預期 phase、CQ id／epoch、CQ_HEAD consumer 用錯圈數或定位錯 slot
CQ 有有效 entry MSI-X 註冊、cause、eventfd、poll 讀取 資料已發布，但通知或等待路徑有問題

service_one() 在 fetch 後先增加 SQ head，再檢查 descriptor epoch。舊 epoch 的路徑增加 STALE_DESC 並返回，不產生 CQ。這是設計行為；若後續正常工作仍假設 SQ／CQ cursor 相同，就會重現 B018 類型的錯誤。

若 CQ 已正確發布，eventfd 沒有新的數值也不能直接判定資料遺失；IRQ 可被遮罩或合併。 反過來，讀到 eventfd 也不能認定某個 CQ entry 已有效。通知與資料驗證是兩個觀測點。

5. DMA fault：把位址、權限、身分分開查

一次 mapping 成功不代表所有方向都可用。SQ 要裝置 READ，CQ 要裝置 WRITE；payload 方向由 opcode 決定。 除三者的 IOVA 範圍外，還需檢查 length、跨頁 chunk、映射所屬 domain 和實際 requester。

假說 支持它的觀測 會推翻它的觀測
payload 沒有 MAP OWNER_MAP 缺對應 kind／範圍；該 payload DMA fault 完整 MAP 且 payload 同方向成功，需要再查其後步驟
DMA 使用錯 requester trace RID 與該 VF BDF 不符 由實際 helper 對同一 VF 記錄的 RID 相符；再查 domain／權限
buffer 長度跨出 mapping fault address／chunk 碰到界外，SQ 輸入能推得同一範圍 全部 chunks 皆在 mapped extent 內；再查方向與世代
WRITE-only 沒禁止 READ READ 實際成功且無 fault，requested flags 卻只列 WRITE strict toy 模式下實際 READ fault；不能僅用 requested flags 判斷
payload 正常，CQ 不可寫 payload 成功，CQ role fault；phase 未發布 CQ body／phase 均成功，問題轉往 consumer／IRQ

B002 的重點是「要求的權限」與「平台真正實現的權限」要分開驗證。 T05 strict WRITE-only 使用明列、預設關閉、限制 toy VF 的 kernel patch； 不可將客製模式的結果套用到 stock Linux。

發生 fault 時還要檢查健康 VF 的整個 buffer 與進度；只有出錯 VF 自己的 errno，不能支持跨 VF 隔離結論。

6. Reset 後掛住：用 tuple 和期限分段

先依相同 VF 和 session，按每個 raw stream 自己的順序排列： 舊 epoch → pending → STOP_REQUEST → PF FENCE（換 epoch）→ 核對 STOPPED → RESET → RECOVERING／RESET_NOTICE → exact UNMAP → fresh CONFIG → READY → REARM。 新 epoch 在 FENCE 時建立，RESET 不再另換一次 epoch。 不同 log 使用的時鐘可能不同，不能直接排序時間戳就聲稱得到全域時序；以 checkpoint／ACK 夾住跨層區間。

現象 檢查點 不應採取的捷徑
一直 RECOVERING 新 CONFIG 與 ready_gen 是否存在？READY 是否仍帶舊 epoch？ 直接寫 ACTIVE 或略過 REARM guard
READY 回覆前就 KILLED logical deadline 與 first/last virtual ticks；是否串行等待其他 owner？ 先延長 timeout，掩蓋 B001 的錯誤順序
reset 完成但舊資料變動 callback old/live tuple、STALE_CPL、新舊 guards、IRQ 只看 cancel counter 或只禁止測試 callback 執行
cleanup 後仍 reserve owner 是否已 closed、PCI/config/outstanding 是否清除？ 直接將 ledger 歸零
exact UNMAP 回傳短長度 requested／returned、fd close、allocation 保留情況 在映射狀態未確認前 free buffer

重要程式片段：過期 callback 必須先被拒絕。 下列摘錄取自 toy_complete()，省略中間的診斷輸出，保留判斷順序：

if (!op->valid) {
    return;
}
if (!same_generation(pf, s, op)) {
    toy_saturate(&s->stale_cpl);
    /* 此處原碼輸出 old/live tuple。 */
    op->valid = false;
    return;
}
if (!gate(pf, vf, op)) {
    op->valid = false;
    return;
}

這段只能支持「經這個入口的舊 tuple 在此返回」。還要往下確認每次 payload／CQ DMA、IRQ 都有 gate， 並檢查測試是否真的執行過有效 retained operation。B010 說明 valid 的讀取時點也會誤導診斷： 呼叫後 valid 被消耗為零，不能反推呼叫前沒有有效工作。

7. 測試工具也在待查範圍內

當 guest 行為看似完整而 host 拒絕時，先讀拒絕的具體 assertion， 把「裝置沒有滿足條件」與「觀測工具弄錯條件」列為兩個獨立假說。

歷史問題 定位方式 修正後仍要保留的要求
B005／B020：JSON 被 printk 插入 對照 serial raw bytes 與 kernel channel；查同時寫 UART 的來源 分流兩個 channel，仍檢查核心診斷與全部必要事件
B008：同值 mapping 事件定位錯 比較第一次／第二次 MAP 的欄位與原始位置 用保存的位置辨識事件，不能刪除 old-UNMAP → new-MAP assertion
B010：讀錯 callback valid 時點 對照呼叫前後 valid 的語意及 STALE_CPL 同時證明呼叫前有效、呼叫後消耗、buffers／IRQ 未變
B016：cold cache 誤判 leak 保存 cold inventory、warm-up、每輪 measured baseline 後續 100 輪仍要求 inventory 收斂，不能把所有成長都叫 cache
B017：新 binary 搭配舊 PASS 比較 run、build stamp、binary、inputs 的 hashes 不自動替歷史結果補新欄位或新 hashes

修 validator 的條件是找到解析／證據語意的具體錯誤，不是「希望案例通過」。 原始 FAIL 應保留；修正後另開新 run，證明修正沒有放寬其他必要條件。

8. 形成最小回歸，再擴大驗證

最小重現要保留觸發條件，移除無關成本。例如 B018 的關鍵是 SQ／CQ 差一， 可以先用真實 owner_workload() 的 native harness 測試，再回 VM 驗證 VFIO 與裝置路徑。 把兩者都做，才能兼顧快速定位與跨層行為。

9. 自問自答：先推理，再看回答

所有 fd 和 mapping 都歸零，但 final flags 是 3，應先查哪裡？ 先按 flags 定義拆成 FENCED|KILLED，再沿裝置 deadline、FLR 與各 owner 退出順序查。資源數量歸零並不反證裝置曾 timeout。 B001 的修正處理跨 owner 的等待順序，沒有延長 core deadline。

SQ head 前進一筆，CQ tail 沒前進，是否一定漏 completion？ 不一定。舊 epoch descriptor 按設計只被消費並增加 STALE_DESC。先查 epoch 與 counter；再確認下一筆正常 request 的 payload 仍按 submission cursor 定位，不能用 CQ slot 猜它的位置。

只修 log 格式，還需要跑真實 VM 嗎？ 若更動影響 UART、ACK 或 channel 選擇，就需要。 Fixture 可檢查解析，但 B020 的第二個失敗是 checkpoint 仍在舊 UART 等 ACK，必須真正完成握手才能發現。

同一筆 retry 成功，是否已修復？ 不是。先分辨先前失敗是否因狀態、時間、輸入或觀測改變； 必須有根因與針對觸發條件的回歸。重跑成功只多了一筆不同執行結果。

如何判斷要加診斷，而不是先加 timeout？ 若不知道卡在哪個契約，先加能區分假說的觀測點： 例如「已寫 CONFIG」與「REARM 核對哪個 tuple」之間的快照。Timeout 只延後結束，通常不增加這項資訊。

測試全部通過後，結論應如何寫？ 寫明版本、輸入、工具、執行範圍與未覆蓋情境。 Native sanitizer、guest KASAN、TCG 整合測試各有不同能力；它們不能共同推出所有時序都沒有 BUG。

SR-IOV 隔離與生命週期指南

本章用問題檢查設計推理；完整狀態／資料流見 系統分析， 實際下命令定位問題見 BUG 定位、反證與修正。 第一次作答時先遮住說明，寫出「管理者、guard、失敗後保留什麼、如何驗證」四項， 再與答案比對。只記術語定義，無法判斷異常路徑是否安全。

PF driver 閱讀順序

可以依下列順序追蹤 PF driver：

  1. Probe 與 unwind：畫出 BAR、IRQ、misc device 的取得順序，挑第二個 IRQ 註冊失敗說明反向回收。
  2. UAPI 與 ownership：從 open file context 說明 lease、ioctl header、replay cache，解釋為何不能只拿 PID 當 owner。
  3. IRQ 與同步：說明 IRQ handler、workqueue、process context 的工作分配，以及 admin → mailbox 的鎖順序。
  4. Lifetime 與 DMA：區分 kref、dying、fence、UNMAP，最後連到 reset 時序圖。

應區分「CPU 正在執行的程式」與「裝置仍可能執行的工作」。 Mutex 可以保護 driver 的管理資料，卻不會自動取消已經取走的 descriptor。 因此必須同時檢查 driver 的同步與裝置工作的取消流程。

為何 insmod 成功還要檢查 probe？

Module registration 成功和裝置綁定成功是兩件事。T02 會檢查失敗時沒有 control node， 並在移除模組後乾淨重試，確認同一個裝置可以正常 probe。只看 insmod 的 return code，可能漏掉裝置初始化失敗。

為何 kref 與 dying 都需要？

kref 確保仍被 file context 引用的記憶體不被提前釋放；dying 阻止已移除裝置的 MMIO。 物件存在不等於 BAR 還有效。回答時沿 toy_open、toy_remove、toy_release_file 各指出一次 reference 操作。

為何 copy_to_user 要放在 event spinlock 外？

Copy 可能遇到 userspace page fault，不能把它放在需要短暫持有的 spinlock 區段。 這裡先將事件搬到 per-open stash，放開鎖後複製；若 copy 失敗，stash 保留供下一次讀取。 Read mutex 序列化同一個 open context 的讀者，event lock 則保護短小的 queue 操作。

Native 32-bit layout check 能代表 32-bit guest 實測嗎？

不能。它檢查 UAPI 結構的大小、offset 與編譯配置；整合 VM 是 x86_64。 Driver 提供 compat_ioctl 的安排，不代表已跑過所有 32-bit userspace 系統呼叫。 應區分實際測試層級與程式的相容性設計。

三種狀態要分開說

Firmware 的 ACTIVE 表示 slot 有可用的已 provision 資源，不單獨保證 queue 正在執行。 第一次 PROVISION commit 後，VF 仍可能 FENCED 且尚未 CONFIG。 是否能 DMA，還要查 config_valid、BME、FENCED、KILLED、generation 及 queue 狀態。

Owner 的 lease/fd/mapping 狀態是另一個維度。Firmware FREE 不會自動關閉 userspace fd； close VFIO fd 也不等於 driver 可以忽略尚未完成的 lease transaction。 用一個「enabled」布林值代表所有層，會丟掉失敗回復需要的資訊。

常見追問與回答重點

為何不把 SR-IOV 當作 IOMMU 隔離保證？

SR-IOV 提供 functions 與 requester 身分；隔離仍取決於拓樸、group、IOMMU domain、 mapping 及 DMA 的實際 requester。這個模型檢查每 group 的成員，禁止 ACS override， 並讓兩個 owner 映射相同 IOVA 做正反向測試。

為何關 BME 還不夠？

Tenant 能經 VF config 存取自己的 BME。管理者的安全保證需要 VF 無法繞過的 PF-only gate， 並在 payload/CQ/IRQ 的真正執行處檢查。BME 仍是必要的 PCI bus mastering 條件，但不是唯一權限。

為何先 fence，再 UNMAP？

UNMAP 是 owner 的位址映射操作；裝置可能已有 descriptor copy 和排程中的 callback。 先確認 fence、generation advance 與 outstanding drain/cancel，才能撤映射。 若 UNMAP size 不符，不可立刻 free buffer；保留 allocation，直到確認 VFIO fd 全部關閉。

eventfd 的數值是否等於 completion 數量？

不能這樣假設。IRQ 可合併或遮罩，eventfd 是通知；有效資料以 CQ phase、id、epoch、status 為準。 Tenant 被喚醒後 drain CQ，再交還 CQ_HEAD。測試同時核對 IRQ 行為和實際 completion 資料。

為何要有 session、epoch 和 token？

Session 區分全域 recovery 前後；epoch 區分該 VF 的世代；cancel token 區分硬體取消的工作。 Lease token 表示管理所有權，ready_gen 表示新的 queue configuration 已完成。 它們的用途不同，不能拿一個單調數字替所有欄位作模糊的「版本檢查」。

裝置 callback 已序列化，為何還需要 lifetime 管理？

本模型的裝置 callback 依 QEMU BQL/main loop 的規則執行；guest 仍有 SMP、IRQ、workqueue、open fd 和 remove。 即使裝置 callback 依序執行，PF driver 仍須管理鎖順序與引用生命週期，防止 guest 端的 UAF。 本版沒有 KCSAN／hostile remove 全矩陣，不能以模型序列化宣稱已驗證所有 guest races。

規格跟 upstream 行為不一樣怎麼辦？

T05 是具體例子：VFIO requested WRITE-only 在 pinned Intel IOMMU second-level mapping 中實際被加上 READ。先保留真實失敗與來源定位，再增加預設關閉、只限 toy VF 的 pinned patch， 使嚴格權限成為明確的實驗條件。不能把通過的客製 kernel 結果描述成 stock Linux 保證。

CRC 能不能證明 secure firmware update？

CRC 能找出部分資料毀損，不能驗證作者身分。本版的 CRC32 是資料工作負載， 不提供 capsule／A/B update，也沒有信任根或簽章驗證；不能把 checksum 稱為 secure update。

用一個 BUG 說明除錯方法

SQ 與 CQ 不一定同步前進

B018 可用兩條 ring 說明：stale descriptor 前 SQ/CQ 同步， 丟棄 stale SQ 後 SQ 比 CQ 多一筆；下一筆工作使用 SQ slot 6，但完成記錄位於 CQ slot 5。 問題不是 CRC 算法錯，而是用完成位置猜原請求的 payload 位置。 修正後將 payload 定位改回 submission cursor，並加入五個 N、正常／差一／wrap 共 15 個 native regression， 保留舊碼實際 EILSEQ 失敗，再跑 sanitizer 與整合 gate。這也說明為何要測異常後的正常工作， 只測異常回覆和 teardown 可能漏掉後續狀態污染。

跨 owner 的時間累積

以 B001 為例，先展示原始 FAIL，再問哪一層失敗。所有 UNMAP、close、reap 都成功， 但最後硬體 flags 是 3，代表 FENCED 加 KILLED。因此問題不在 mapping size 或 child leak。 往前對齊 FLR、RECOVERING、deadline 與各 owner 關閉順序，才找到時間累積的根因。

修正沒有延長 deadline：先送出所有停止，再等待每個 owner；最後一個 lease 釋放後立即 disable。 驗證也不是只重跑到一次成功，還強化 validator 的跨 owner 順序檢查，保留兩次 100 輪證據， 並跑受影響的 M1/M2/M3 回歸。完整狀態請見 BUG_LOG.md。

更深入的追問

為何不用一個 global mutex 包住全部操作？

Mutex 能序列化部分 host threads，無法回收已被 device fetch 的 descriptor，也不能代替 VFIO domain。 還要考慮 IRQ callback 不能睡眠、等待 ACK 的 thread 不應阻擋完成它的 worker。 本版 admin_mutex → mbx_mutex 有固定順序；remove／fd lifetime 另需引用保護。不要宣稱一把鎖解決所有時序問題。

DMA helper 成功一次，整筆工作就成功了嗎？

不是。SQ fetch、payload 各 chunk、CQ body、CQ phase 都可能各自 fault。 每次 helper 都核對回傳值；跨頁寫可能部分成功，不保證 transaction rollback。 即使 payload 完成，CQ 失敗也必須保守 fence，不能只回一個猜測成功的 IRQ。

為何需要獨立 oracle？

把實作表格直接複製成預期值，兩邊可能一起錯。Native Python oracle 以獨立模型核對 C core 操作， ring oracle 以 FIFO 比較 u32 wrap；guest validator 則從 raw records 核對跨層關係。 它們提供不同角度，但仍受輸入預算與模型假設限制。

KASAN 通過能證明沒有 race 嗎？

不能。KASAN 幫助偵測受測 kernel 路徑的越界與 UAF，不等於 race detector。 本版只保留已驗證的 KASAN 情境；沒有 KCSAN 與所有 hostile hot-remove 的實測結果。 測試結果受執行路徑和工具能力限制。

跨 u32 wrap 為何仍能算 pending？

Counter 使用 unsigned arithmetic，tail - head 按 2^32 取模；前提是有效 outstanding 永遠有界且不超過 N。 Array index 再取 counter & (N-1)，phase 依 counter/N 的圈數交替。 不能用 signed subtraction，不能只保存 masked index，也不能忽略 pending > N 的非法輸入。

為何 retained quota 比直接歸零更安全？

失敗的 release 表示仍不確定資源是否可重用。歸零會讓下一個 owner 再次分配同一份資源， 把未清理的狀態交給別人。保留 quota 限制可用容量，但讓錯誤顯性存在，直到明確 recovery 成功。

軟體模型的價值及限制是什麼？

價值是可控制 requester、logical clock、fault checkpoint 與 retained callback，使跨層錯誤可重現。 Linux PCI/VFIO/IRQ 路徑實際執行，能練習 driver 與協定設計。 限制是沒有真實 PCIe 電氣／cache coherency／功耗／吞吐與板級韌體部署證據。

情境推演：修改條件後會發生什麼

情境一：Tenant 已寫完 queue bases，可否立即 doorbell？

先預測。 此時 core 可能已是 ACTIVE，且 SQ／CQ 的 IOVA 都合法；還缺哪個條件？

推導。 分次寫入只更新 staging。config_commit() 驗證完整設定後才複製到 live config， 並設為 READY_PENDING。接著 owner 的 READY tuple 必須經 labd／PF 核對， fw_rearm() 再確認 epoch、ready_gen、BME、fenced、無 outstanding、未 killed 和 deadline，才由 HAL 開 gate。 單獨寫 bases 或 CONFIG_COMMIT 都不是 DMA 授權。

讀碼位置。 device/toy_vf.c 的 config_commit()／write_vf() → fwcore/admission.c 的 fw_rearm() → device/fw_adapter.c 的 hal_gate()。

檢查答案。 應同時說出「staging 與 live config 不同」和「READY_PENDING 仍 fenced」。 若只說 queue 地址是否合法，尚未回答誰有權開 DMA。

情境二：A 已 reset，舊 callback 延遲到新 queue RUNNING 才到達

先預測。 新 queue 已 RUNNING，為何 gate 還能拒絕舊 callback？

推導。 新 live tuple 的 epoch/token 已變；舊 operation 帶著當時的 tuple。 toy_complete() 先比 same_generation()，不符便增加 STALE_CPL 並消耗該 operation。 即使目前 queue 合法、BME 打開、core ACTIVE，這筆舊 operation 仍不屬於現在的世代。 新 queue 可工作與舊工作可完成，是兩個不同命題。

如何反證修正不完整。 如果僅檢查 callback 在 fenced 階段被擋，會漏掉重開 gate 後的情況。 T08 分別在 fresh config 仍 fenced，以及 REARM 後執行真實 retired callback，檢查新舊 buffers、CQ 和 IRQ。 應從 validate_recovery() 找到兩次 callback 的必要條件。

情境三：Payload 已改變，但寫 CQ phase 時 fault

先預測。 可否直接發 IRQ，讓 tenant 知道 payload 完成了？

推導。 不可。協定以有效 CQ entry 宣告結果；phase 尚未成功發布，就沒有可接受的 completion。 toy_complete() 先寫 body，最後單獨寫 phase；任何 CQ DMA 失敗就 toy_fail()， 不會經成功路徑增加 CQ tail 或發 completion IRQ。payload 的部分或全部副作用可能已存在， 錯誤處理不能宣稱跨所有 DMA 有 transaction rollback。

檢查答案。 應說明 owner 必須把受影響的 outstanding request 當作失敗處理並協調 reset， 不能因 buffer 看起來像預期值就自行宣告完成。讀碼位置在 toy_complete() 的 body／phase 寫入與 s->cq_tail++ 之間。

情境四：VFIO UNMAP 回傳長度小於 requested，接著 close 成功

先預測。 最後所有 fd 都關掉，是否可以把整個 cleanup 改成成功？

推導。 不能。安全回收與測試是否成功是兩件事。程式可在 UNMAP 不完整時保留 allocation， 先關閉 owner 的 VFIO device／group／container，讓映射生命週期收斂後才釋放 RAM； 但應保留先前的 failure。否則就把已發生的契約違反藏在成功 teardown 裡。

讀碼位置。 lab_vfio_close() 的 failed 累積與 guest/tenant/owner.c 的 owner mapping cleanup。 應辨認 baseline VFIO helper 與三種 OWNER_MAP 的實作各自保存哪些狀態，不要將兩套結構混用。

情境五：FREE、reserve=0，但 flags 同時有 KILLED

先預測。 是否可直接開始下一輪 PROVISION？

推導。 不可只看 FREE。fw_create() 拒絕 killed hardware；FREE 是 core 資源狀態， KILLED 是硬體 gate 狀態。FAILED 經 DESTROY／RELEASE 可以釋放 ledger， 但 KILL 仍保留到 global recovery。乾淨基線要檢查全部 slots 的 core、flags、config、outstanding、lease。

如何驗證。 對照 fw_create()、 fw_global_recover() 及測試 validator 的 final snapshot。 若只是將 state 或 reserve 手動歸零，沒有證明全域復原前提成立。

情境六：本地圖文正常，推上 GitHub 後連結失效

先預測。 問題可能不在 Markdown 語法，還缺哪項發布條件？

推導。 本地存在的 ignored artifacts、build outputs 或 HTML viewer 不一定能在 GitHub 取得。 公開入口應指向 tracked Markdown、SVG 與 source；離線 HTML 供下載後開啟。 本地連結檢查還需採公開檔案集合，不能因開發目錄剛好存在 raw log 就建立可點擊連結。 B023 是這種差異的實際案例。

檢查答案。 應分開驗證相對路徑／anchor 正確，以及 target 真的會隨 repository 發布。 教材生成成功只表示文件檢查通過，不能替代裝置／driver 的 M0–M3 驗收。

兩筆修正的程式推導

以下從現有修正碼重建因果關係；數字案例是推導範例，不是額外的動態觀測。

B001：把等待順序寫成可檢查的契約

lifecycle_case() 中兩個迴圈有不同責任：第一個發出 fenced stop， 第二個確認退出並 release。程式保留兩階段，避免第一個 VF 先進 RECOVERING， 卻在其他 owner 尚未開始停止時累積等待時間。

if (!failed) for (unsigned vf=0;vf<4;vf++)
    if (owner_stop_begin(&owners[vf])) { failed=1; break; }
if (!failed) for (unsigned vf=0;vf<4;vf++)
    if (owner_stop_finish(&owners[vf])||release_owner(&owners[vf])) { failed=1; break; }

驗證器檢查的是「全部 fence 事件先於第一個 reap」，而非僅要求最後都退出。 這個相對順序可以揭露相同錯誤再次出現；單看 final fds/maps=0 無法判斷中間是否已 timeout。

B018：兩個 cursor 必須各司其職

假設 N=16，正常處理 5 筆後 SQ head=5、CQ tail=5。再消費一筆 stale descriptor， SQ head 變 6、CQ tail 仍為 5。下一筆正常請求來自 SQ slot 6，它的 completion 會放 CQ slot 5。

時點 SQ head CQ tail 下一筆正常 payload 的定位依據
5 筆正常工作已完成 5 5 submission cursor
stale descriptor 已消費 6 5 submission cursor 6，不能取 CQ slot 5
下一筆正常工作已完成 7 6 completion id 應對應那筆 submission

owner_workload() 分開計算兩個 index：

uint32_t index=lab_ring_index(o->cq_head,o->entries);
/* index 用於 CQ entry。 */
uint32_t payload_index=lab_ring_index(start+received,o->entries);
/* payload_index 用於原始 submission 所屬的 payload。 */

回歸必須在 stale 輸入之後再做正常工作，才能確認異常處理沒有污染後續資料流。 只驗「stale 沒有 CQ」再立即 teardown，無法覆蓋這個錯誤。
